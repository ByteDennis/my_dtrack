 DTRACK — CLI HANDOFF GUIDE
================================================================================

Author:  Dennis
Updated: 2026-05-18
Goal:    Reproduce the entire web-UI workflow from bash. Every step the web
         wizard does is a single CLI command. `dtrack serve` is never required.


================================================================================
 1. INSTALL & ENV
================================================================================

Install (editable, with platform extras as needed):
    uv pip install -e '.[oracle,aws]'              # or: pip install -e ...

Resolve env (looked up in this order, first hit wins):
    1) --env <path>
    2) $DTRACK_ENV_FILE
    3) dtrack.conf | .env | dtrack.env walked up from cwd
    4) ~/.dtrack/dtrack.conf, /etc/dtrack/dtrack.conf

Inspect what got picked up:
    dtrack doctor

Required vars (by platform):
    Oracle : PCDS_USR, <macro>_pwd  (one per service in MACRO2SVC + overrides),
             optional LDAP_DSN with '{service}' placeholder
    AWS    : AWS_DEFAULT_REGION, AWS_S3_WORK_GROUP, AWS_S3_STAGING_DIR,
             AWS_TOKEN_URL, AWS_ARN_URL, AWS_USR, AWS_HOST, AWS_PWD
    SAS    : SAS_LIB, OUT_DIR, EMAIL_TO, SAS_CACHE_DIR


================================================================================
 2. ONE-SHOT END-TO-END
================================================================================

    dtrack run project.db --config pairs.json \
        --outdir ./out --type both --vintage day -y \
        --html-row ./out/output/compare_row.html \
        --html-col ./out/output/compare_col.html

`dtrack run` does: init → extract (per platform) → load → compare → HTML.
`-y` skips every HITL prompt. Drop it to get interactive skip/ignore
prompts on mismatched dates and column mappings.

Per-stat control (passed through to gen-aws/gen-oracle):
    --preset quick|standard|detailed
    --stats-override n_unique=on,hash_sum=off,top_10=on,...

Stat keys (see dtrack/constants.py STATS_PRESETS):
    n_total, n_missing, n_unique, min_max, length, hash_sum, top_10
The CSV always emits the 14-col schema; disabled stats land as empty
strings. preset is the SQL pathway; stats_override is authoritative.


================================================================================
 3. THE 8 STEPS — UI PAGE → CLI EQUIVALENT
================================================================================

Each web wizard step maps 1-to-1 to a CLI command.

    UI page          CLI command                                    Notes
    ---------------  ---------------------------------------------  ----------------------------
    /pairs           edit pairs.json directly OR `dtrack init`      No CLI form-builder; the
                                                                    JSON is the source of truth.
    /load_row        dtrack load-row <db> <folder> --config         CSV → _row_counts
    /row_compare     dtrack compare-row <db> --config --html        also writes _row_comparison
    /col_mapping     dtrack match-columns <db> --config             auto-match + interactive
    /col_gen         dtrack gen-aws|gen-oracle|gen-sas              emits SQL/SAS + runs Athena/Oracle
    /load_col        dtrack load-col <db> <folder> --config         CSV → _col_stats
    /col_compare     dtrack compare-col <db> --config --html        per-col diffs + HTML
    /benchmark       (no CLI; web-only)                             not part of e2e compare


================================================================================
 4. BASH-SCRIPT TEMPLATE FOR ONE COMPARISON
================================================================================

Drop this in run.sh, edit paths, then `bash run.sh`.

    #!/usr/bin/env bash
    set -euo pipefail

    DB=./project.db
    CFG=./pairs.json
    CSV=./csv     # AWS / Oracle CSV output
    SAS=./sas     # SAS script output
    OUT=./output  # HTML reports

    mkdir -p "$CSV" "$SAS" "$OUT"

    # 1. init DB (idempotent; --migrate to upgrade schema in place)
    [ -f "$DB" ] || dtrack init "$DB" --config "$CFG"

    # 2. discover columns (live or from CSV metadata dump)
    dtrack load-columns "$DB" --config "$CFG"
    # or: dtrack load-columns "$DB" --config "$CFG" --csv meta.csv

    # 3. auto-match column names between left/right
    dtrack match-columns "$DB" --config "$CFG" --mode merge

    # 4. extract per platform (parallel-safe; run only those you need)
    dtrack gen-aws    "$CFG" --outdir "$CSV" --type both --db "$DB" \
                      --preset standard
    dtrack gen-oracle "$CFG" --outdir "$CSV" --type both --db "$DB" \
                      --preset standard
    dtrack gen-sas    "$CFG" --outdir "$SAS" --type both --db "$DB"
    # If you ran gen-sas you still have to execute the .sas files in a
    # SAS session yourself; they write CSVs into $SAS.

    # 5. load extracted CSVs back into the SQLite project DB
    dtrack load-row "$DB" "$CSV" --config "$CFG"
    dtrack load-col "$DB" "$CSV" --config "$CFG"
    # (re-run with --folder "$SAS" for SAS-side outputs)

    # 6. compare + emit HTML reports (-y for non-interactive)
    dtrack compare-row "$DB" --config "$CFG" -y \
                       --html "$OUT/compare_row.html"
    dtrack compare-col "$DB" --config "$CFG" -y \
                       --html "$OUT/compare_col.html"


================================================================================
 5. pairs.json STRUCTURE (the source of truth)
================================================================================

Everything the web UI persists ends up here. Hand-edit or generate. The
DB caches a copy in _table_pairs; sync via `compare-row`/`compare-col`
(both call sync_config_to_db) or `dtrack run`.

    {
      "pairs": {
        "loans": {
          "left":  { "source": "oracle", "table": "SCHEMA.LOANS",
                     "conn_macro": "pb23", "date_col": "RPG_DT",
                     "date_type": "date",  "vintage": "day",
                     "where": "" },
          "right": { "source": "aws",    "table": "db.loans",
                     "conn_macro": "loans_db", "date_col": "rpg_dt",
                     "date_type": "date",  "vintage": "day",
                     "where": "" },
          "skip": false,
          "description": "Loan portfolio daily comparison",
          "col_map":           { "ACCT_ID": "acct_id" },
          "col_type_overrides": {},
          "ignore_rows":    [],
          "ignore_columns": [],
          "where_map":   { "left": "", "right": "" },
          "comment_map": { "row": {"left":"","right":""},
                            "col": {"left":"","right":""} },
          "time_map":    { "row": {"left":"","right":""},
                            "col": {"left":"","right":""} }
        }
      },
      "metadata": { "title": "...", "subtitle": "..." }
    }

Notes:
- The qualified table name `{source}_{pair_name}` is the key for
  _row_counts / _col_stats / _metadata. Built by platforms.base.qualified_name.
- `where_map` is rebuilt automatically by `compare-row` from
  matching/excluded dates; you don't normally edit it.
- `ignore_rows` / `ignore_columns` are how non-interactive runs persist
  HITL decisions across invocations.


================================================================================
 6. DATA THAT FLOWS BETWEEN STEPS
================================================================================

    SQLite tables (in <project_db>):
      _metadata        per-table source, date_var, vintage, date range
      _row_counts      (source_table, dt) → row_count
      _col_stats       (source_table, column, dt) → 14-field stat row
      _column_meta     (source_table, column, data_type, source)
      _table_pairs     pair_name → left/right tables + col_mappings (JSON)
      _row_comparison  pair_name → overlap, matching/excluded dates (JSON)
      _col_comparison  pair_name → columns_compared, diff_columns, details

    Inspect anytime:
      dtrack query <db> "SELECT * FROM _row_comparison LIMIT 5"
      dtrack query <db> "SELECT * FROM _col_stats WHERE source_table='aws_loans' LIMIT 5"

The matching_dates list in _row_comparison is what makes col extraction
meaningful: gen-aws/gen-oracle filter their col SQL to those dates only,
so column stats are always compared on dates where row counts agreed.


================================================================================
 7. PRESET / STATS_OVERRIDE — WHAT IT ACTUALLY CONTROLS
================================================================================

Preset selects the SQL generation pathway (quick = single-pass aggregates,
detailed = freq-table-derived top_10, etc.). stats_override is applied
on top — it can blank an individual stat the preset would have computed,
but it cannot enable a stat the preset's SQL didn't compute.

Effective rule for the 14-col CSV:
    output[stat] = '' if stats_override.get(stat) is False else preset_default

In practice:
    --preset quick                              → fastest, no n_unique/hash/top_10
    --preset standard                           → +n_unique +hash_sum
    --preset detailed                           → +top_10 (full)
    --preset standard --stats-override hash_sum=off
                                                → standard SQL, but hash_sum blanked

Platform coverage:
    gen-oracle   honored at SQL-gen time (build_col_sql) AND output mask
    gen-aws      honored at SQL-gen time for file path; live cursor path
                 still issues full SQL but blanks disabled fields in CSV
    gen-sas      preset='quick' aliases to coarse=True. stats_override is
                 not honored on the SAS template; CLI warns if passed.


================================================================================
 8. INCREMENTAL & DEBUGGING
================================================================================

Incremental date window (every extract command + run):
    --from-date 2026-01-01 --to-date 2026-04-30

Only re-run a slice of the pipeline:
    dtrack run ... --skip-extract               (re-load + compare only)
    dtrack run ... --skip-load                  (re-compare only)
    dtrack run ... --skip-compare               (just refresh CSVs + DB)

Mock mode (no network, fixtures-driven dev):
    DTRACK_MOCK=./fixtures dtrack gen-aws    ...
    DTRACK_ATHENA_MOCK=...  dtrack gen-aws   ...   (athena-only)
    DTRACK_ORACLE_MOCK=...  dtrack gen-oracle ...  (oracle-only)
The mock directory must contain `{qname}_row.csv` / `{qname}_col.csv` /
`{qname}_columns.csv` matching what extraction would normally produce.

Schema upgrade after a dtrack version bump (data-preserving):
    dtrack init <db> --migrate

Ad-hoc SQL against the project DB:
    dtrack query <db> "SELECT pair_name, matching_dates FROM _row_comparison"
    dtrack query <db> --write "DELETE FROM _row_counts WHERE source_table='...'"

Debug breakpoints:
    dtrack --debug ipdb run ...                 (drop into ipdb on crash)
    dtrack --debug attach run ...               (debugpy on 0.0.0.0:5678)


================================================================================
 9. PLATFORMS — WHO RUNS WHAT
================================================================================

    Source ↓        Command          What it produces
    oracle          gen-oracle       runs SQL via oracledb;
                                     writes {qname}_row.csv, {qname}_col.csv
    aws             gen-aws          runs SQL via pyathena;
                                     writes {qname}_row.csv, {qname}_col.csv
                                     plus extract_row.sql / extract_col.sql
                                     so the same SQL can be replayed
    sas / hadoop    gen-sas          writes ONE combined .sas file. You
                                     execute it in a SAS session; it writes
                                     {qname}_row.csv / {qname}_col.csv into
                                     --outdir.

A pair can mix sources (e.g., left=oracle, right=aws). Run all the
extractors that have at least one table on their side, then load both
folders.


================================================================================
10. WHERE TO LOOK WHEN SOMETHING BREAKS
================================================================================

    Symptom                                   Investigate
    ----------------------------------------  ----------------------------------
    "Database not found"                      run `dtrack init <db>` first
    "Config file not found"                   pass --config <path>
    "Pair not found"                          pairs.json doesn't list the pair,
                                              or compare-row never ran to sync
                                              it into _table_pairs
    "No columns specified for ..."            run `dtrack load-columns` first
    "No matching dates"                       run compare-row before compare-col
    Dates parsed wrong                        python -c "from dtrack.date_utils \
                                              import parse_date; print(parse_date('YOUR'))"
    Athena auth fails                         dtrack doctor → check AWS_* + AWS_PWD
    Oracle auth fails                         dtrack doctor → check <macro>_pwd
    SAS .sas script wrong                     check `date_type` per side; SAS
                                              wants 'DDMONYYYY'd, Oracle/Athena
                                              want DATE 'YYYY-MM-DD'
    Tests                                     pytest tests/ -x -q     (must stay green)
