================================================================================
 DTRACK — CLI HANDOFF GUIDE
================================================================================

Author:  Dennis
Updated: 2026-06-27
Goal:    Reproduce the entire web-UI workflow from bash. Every step the web
         wizard does is one or more CLI commands. `dtrack serve` is optional.

The pipeline is GENERATE → RUN → LOAD → COMPARE:
    generate   write extract_{row,col}.<platform>.sql (NO backend hit)
    run-sql    execute that SQL against each backend -> {qname}_{row,col}.csv
    load-*     CSV -> SQLite project.db (_row_counts / _col_stats)
    compare-*  diff left vs right -> _row_comparison / _col_comparison + HTML
`dtrack extract` = generate + run-sql in one shot. There is NO `dtrack run`.


================================================================================
 1. INSTALL & ENV
================================================================================

Install (editable, with platform extras as needed):
    uv pip install -e '.[oracle,aws,csv]'          # or: pip install -e ...
    # csv source needs duckdb; databricks/hadoop pull their own driver extras.

Resolve env (looked up in this order, first hit wins):
    1) --env <path>
    2) $DTRACK_ENV_FILE
    3) dtrack.conf | .env | dtrack.env walked up from cwd
    4) ~/.dtrack/dtrack.conf, /etc/dtrack/dtrack.conf

Inspect what got picked up:
    dtrack doctor

Required vars (by platform):
    Oracle     : PCDS_USR, <macro>_pwd (one per service in MACRO2SVC +
                 DTRACK_ORACLE_MACROS), optional LDAP_DSN with '{service}'
    AWS/Athena : AWS_DEFAULT_REGION, AWS_S3_WORK_GROUP, AWS_S3_STAGING_DIR,
                 AWS_TOKEN_URL, AWS_ARN_URL, AWS_USR, AWS_HOST, AWS_PWD
    Hadoop/Hive: a working ODBC DSN (HADOOP_DSN, default 'Hive_Prod')
    Databricks : per the databricks driver env (catalog.schema in conn_macro)
    CSV        : no creds — read in-process via DuckDB


================================================================================
 2. SUPPORTED SOURCES
================================================================================

    source       engine / driver         conn_macro means
    -----------  ----------------------  --------------------------------------
    oracle       oracledb (direct)       Oracle service macro (pb23, pb30, ...)
    hadoop       pyodbc / Hive           Hive database name
    aws          pyathena (Athena)       Athena database name
    databricks   databricks sql          "catalog.schema"
    csv          DuckDB (in-process)     filesystem path to the .csv file

A pair can mix sources (e.g. left=oracle, right=aws). Generate/run each
platform that has at least one table; load both result folders.
(SAS support has been removed.)


================================================================================
 3. ONE COMPARISON, END-TO-END (bash)
================================================================================

    #!/usr/bin/env bash
    set -euo pipefail
    DB=./project.db
    CFG=./pairs.json
    BASE=./out                 # csv/ is derived as $BASE/csv

    # 1. init DB (idempotent; --migrate upgrades schema in place)
    [ -f "$DB" ] || dtrack init "$DB" --config "$CFG"

    # 2. columns: load defs (inline `columns` / `columns_file` in pairs.json
    #    win and skip live discovery; otherwise discovered from the backend)
    dtrack load-columns "$DB" --config "$CFG" --columns-dir "$BASE/csv"

    # 3. auto-match column names left<->right (writes col_map)
    dtrack match-columns "$DB" --config "$CFG" --yes      # --map-csv optional

    # 4a. ROW: generate -> run -> load -> compare
    dtrack generate "$DB" --config "$CFG" --outdir "$BASE" --type row
    dtrack run-sql  "$DB" --config "$CFG" --outdir "$BASE" --type row
    dtrack load-row "$DB" "$BASE/csv" --config "$CFG"
    dtrack compare-row "$DB" --config "$CFG" -y --html "$BASE/output/compare_row.html"

    # 4b. COL: must run AFTER compare-row (col SQL is scoped to matching dates)
    dtrack generate "$DB" --config "$CFG" --outdir "$BASE" --type col \
                    --preset standard
    dtrack run-sql  "$DB" --config "$CFG" --outdir "$BASE" --type col
    dtrack load-col "$DB" "$BASE/csv" --config "$CFG"
    dtrack compare-col "$DB" --config "$CFG" -y --html "$BASE/output/compare_col.html"

Shortcut: `dtrack extract "$DB" --config "$CFG" --outdir "$BASE" --type both`
runs generate+run-sql together. Per-platform one-shots also exist:
gen-aws / gen-oracle / gen-databricks (<config> --outdir --db --type ...).

ORDER MATTERS: row-compare must precede col generate/extract — column stats
are only computed on the dates where row counts agreed (matching_dates in
_row_comparison). Running col first yields no/!wrong date scope.


================================================================================
 4. THE `just` E2E PIPELINE (recommended driver)
================================================================================

The justfile wraps the whole flow with skip-caching and one run.log.

    just e2e row                 # generate+run row -> discover -> load -> compare
    just e2e col-gen             # match-columns -> generate col SQL (NO run)
    just e2e col-run             # run col SQL -> load-col -> compare-col
    just e2e col                 # col-gen then col-run
    just e2e all                 # row, then col   (default)

Forwarded extract/generate flags:
    --vintage day|week|month|quarter|year|all
    --preset quick|standard|detailed
    --stats-override n_unique=on,hash_sum=off,...
    --from-date / --to-date YYYY-MM-DD
    --clean[=reports|rebuild|all]    run e2e-clean first (default rebuild)

Variables: pair=NAME (use testing/NAME.json), force=1 (ignore skip-cache),
resultdir=DIR, config=PATH, db=PATH.

CLEAN TIERS (also `just e2e-clean <level>`), by distance from the backend —
each tier a superset of the one above:
    reports  rm compare_*.{html,xlsx}         -> re-compare (instant)
    rebuild  + project.db* + .state sentinels  -> re-load + re-compare; KEEPS
             csv/ extracts & caches -> NO backend hit  (default)
    all      + csv/ (extracts + cached query db + materialized csv.duckdb)
             -> full re-extract (HITS backend)
    Always kept: pairs.json, output/run.log


================================================================================
 5. CSV SOURCE (DuckDB, in-process)
================================================================================

For source=csv, dtrack materializes each CSV ONCE into a typed DuckDB table
so every query is `FROM <table>` (short SQL, parse-once, consistent typing):

    <outdir>/csv/.state/csv.duckdb     CREATE TABLE t_<qname> per CSV
    <outdir>/csv/.state/.cache.db      query-result cache (all sources)

Column types (numeric vs categorical etc.) come from the SAME explicit types
used to build the table, so stats can't disagree with the read. Type source,
in precedence order:
    1) inline `columns` in the pair side config  (config wins, skips DESCRIBE)
    2) `columns_file` path in the pair side config (variable,data_type CSV)
    3) {qname}_columns.csv sidecar in the csv outdir
    4) DuckDB DESCRIBE inference (only if none of the above)
A hand-edited {qname}_columns.csv is never overwritten.


================================================================================
 6. COLUMN DEFINITIONS (avoid live discovery)
================================================================================

Discovery (DESCRIBE / information_schema / ALL_TAB_COLUMNS) is skipped whenever
a definition is already present, for ALL sources:
    - inline `columns: {VAR: TYPE}` under pairs.<p>.<side>
    - `columns_file: <path>` under pairs.<p>.<side>  (variable,data_type CSV)
    - a {qname}_columns.csv sidecar (load via `dtrack load-columns`)
Discovery results are written to {qname}_columns.csv and _column_meta so the
next run is offline.


================================================================================
 7. pairs.json STRUCTURE (the source of truth)
================================================================================

    {
      "pairs": {
        "loans": {
          "left":  { "source": "oracle", "table": "SCHEMA.LOANS",
                     "conn_macro": "pb23", "date_col": "RPT_DT",
                     "date_type": "date", "vintage": "day", "where": "",
                     "columns": { "ACCT_ID": "VARCHAR2", "BAL": "NUMBER" } },
          "right": { "source": "csv", "table": "loans",
                     "conn_macro": "/data/loans.csv", "date_col": "rpt_dt",
                     "date_type": "string_dash",
                     "columns_file": "/data/loans_cols.csv" },
          "fromDate": "2026-01-01", "toDate": "2026-04-30",
          "strict": false, "skip": false,
          "col_map": { "ACCT_ID": "acct_id" },
          "col_filter": { "include": [], "exclude": [] },
          "col_type_overrides": {},
          "ignore_rows": [], "ignore_columns": [],
          "where_map": { "left": "", "right": "" }
        }
      },
      "date_types": { },                 // optional custom date_type registry
      "metadata": { "title": "...", "subtitle": "..." }
    }

date_type values (constants.DATE_COLUMN_TYPES): date, timestamp, datetime,
num (YYYYMMDD), num_yyyymm, string_dash (YYYY-MM-DD), string_compact
(YYYYMMDD), string_mon (DDMONYYYY), string_mon_dash (DD-MON-YYYY),
string_us (MM/DD/YYYY). pair fromDate/toDate are rendered into each WHERE in
the column's stored shape (e.g. string_compact 2026-05-02 -> '20260502') and
the date-bounds clause is emitted FIRST, then the table's `where`.

Notes:
- Qualified table name = "{source}_{name}" (platforms.base.qualified_name);
  it keys _row_counts / _col_stats / _metadata / _column_meta.
- where_map is rebuilt by compare-row from matching/excluded dates.
- ignore_rows / ignore_columns persist non-interactive (-y) HITL decisions.
- vintage / strict can be set per-pair or per-side.


================================================================================
 8. PRESET / STATS_OVERRIDE
================================================================================

Stat keys (constants.STATS_PRESETS):
    n_total, n_missing, n_unique, min_max, length, hash_sum, top_10
Presets:
    quick     fastest; no n_unique / hash_sum / top_10
    standard  + n_unique + hash_sum
    detailed  + top_10 (full)
--stats-override n_unique=on,hash_sum=off,... is authoritative: it can blank a
stat the preset computed AND (in the override path) toggle individual stats.
The 14-col CSV schema is always emitted; disabled stats land as ''.
hash_sum is an exact 16-bit MD5-based categorical hash; n_unique is exact
COUNT(DISTINCT) (APPROX_* is never emitted).


================================================================================
 9. DATA THAT FLOWS BETWEEN STEPS (SQLite tables in <project_db>)
================================================================================

    _metadata        per-table source, date_var, vintage, date range
    _row_counts      (source_table, dt) -> row_count
    _col_stats       (source_table, column, dt) -> 14-field stat row
    _column_meta     (source_table, column, data_type, source)
    _table_pairs     pair_name -> left/right + col_mappings/filters (JSON)
    _row_comparison  pair_name -> overlap, matching/excluded dates (JSON)
    _col_comparison  pair_name -> columns_compared, diff_columns, details

    dtrack query <db> "SELECT * FROM _row_comparison LIMIT 5"
    dtrack query <db> --write "DELETE FROM _row_counts WHERE source_table='...'"


================================================================================
10. LOGGING (output/run.log)
================================================================================

DTRACK_LOG sets the path (justfile points it at <e2edir>/output/run.log).
    - Each CLI command opens with a thick ==== banner, so recipe calls are
      clearly separated.
    - Every query logs whether it was served from cache or the live backend:
        "query: CACHE HIT (N rows) scope=..."
        "query: LIVE DB read -> cached (N rows) scope=..."
        csv also logs "live read from materialized DB <path>".
    - DTRACK_LOG_LEVEL (default DEBUG) controls file verbosity.


================================================================================
11. INCREMENTAL, CACHE & DEBUGGING
================================================================================

Incremental window (generate / run-sql / extract / gen-* / compare-*):
    --from-date 2026-01-01 --to-date 2026-04-30

Query cache: results cached in <outdir>/csv/.state/.cache.db. Disable with
DTRACK_QUERY_CACHE=0. `run-sql --resume` skips blocks whose CSV already exists.
`force=1` (justfile) ignores the .state skip-cache sentinels.

Testing against real backends (mock mode has been removed entirely):
    pytest tests/containers --run-containers
spins up dockerized Oracle / Trino / Hive / Spark via testcontainers, seeds
synthetic data, and runs the full pipeline (incl. test_e2e_pipeline.py:
init -> load -> compare). tests/integration/ runs the same flow against real
remote tables (`--run-live`).

Schema upgrade after a version bump (data-preserving):
    dtrack init <db> --migrate

Debug:
    dtrack --debug ipdb <cmd> ...      (drop into ipdb on crash)
    dtrack --debug attach <cmd> ...    (debugpy on 0.0.0.0:5678)


================================================================================
12. WHERE TO LOOK WHEN SOMETHING BREAKS
================================================================================

    Symptom                              Investigate
    -----------------------------------  ----------------------------------
    "Database not found"                 dtrack init <db> first
    "Pair not found"                     pairs.json missing the pair, or
                                         compare-row never synced _table_pairs
    "No columns specified for ..."       load-columns, or set columns /
                                         columns_file in pairs.json
    "No matching dates"                  run compare-row before col gen/compare
    wrong date literal in WHERE          check date_type per side (sec. 7)
    csv types look wrong                 check the materialized csv.duckdb:
                                         DESCRIBE t_<qname>; fix `columns`
    Athena/Oracle auth fails             dtrack doctor -> AWS_* / <macro>_pwd
    stale JS in web UI                   hard-reload; assets are revalidated
    anything                             tail output/run.log (sec. 10)
    Tests                                pytest tests/ -x -q   (must stay green)
                                         real backends: pytest --run-containers
