DTRACK CLI GUIDE — config -> row -> col (compact complete edition)
================================================================

0. MODEL
--------

Distributed:
  dtrack_left (on-prem) <---- S3 run payloads ----> dtrack_right (Databricks Job)

Local fallback:
  python -m dtrack_local uses a local directory with the same payload layout.
  `_local/data.duckdb` is for inspection; it is not the protocol source of truth.

Stage 1 / row:
  Left counts each date partition. Right counts the same partitions, reconciles them,
  and applies the configured Version 1 or Version 2 barrier.

Stage 2 / col:
  Left and Right independently select the same records, compute per-column statistics,
  and Right writes one comparison result per pair x vintage window x mapped value column.

All auxiliary commands are under `dtrack tools`; old root commands are intentionally absent.

Config versions:
  version: 1  Right reconciles counts, then releases matching partitions to Left Stage 2.
  version: 2  Left runs first from the config; Right later fails if any mismatch is not listed
              in excluded_partitions, otherwise it computes and compares current-plan statistics.

Debug the main workflows directly:

  dtrack left-run --config config.json --debug ipdb
  dtrack row-check --config config.json --debug ipdb
  dtrack col-check --config config.json --debug attach            # debugpy port 5678
  dtrack local run --config config.json --debug ipdb

Debug left-run, row-check, col-check, or local directly with `--debug ipdb|attach`.

Terminal mode uses ipdb and opens post-mortem on unhandled runtime errors.

Executable learning cases live only in `examples/nbs`:

  00_row_check.ipynb   distributed Left Stage 1 + Databricks Job hand-off
  01_col_check.ipynb   distributed Left Stage 2 + Databricks compare/report
  02_local.ipynb       one-process run through Databricks SQL Warehouse
  03_tools.ipynb       doctor, materialize, report, rollback, debug, dbx, blog
  04_common.ipynb      date, hash, manifest, sampling, and statistics contracts
  05_reuse_pulled.ipynb statistics + report from the windows an earlier local run already pulled

They load `examples/e2e/config.json` and its deterministic generated data. The five notebooks also
group every current unit-test module by domain and demonstrate its important contracts through
direct production-API assertions, not a pytest launcher. Markdown is limited to the title;
executable cells carry short comments beside the real public CLI commands and assertions.


1. INSTALL + ENVIRONMENT
------------------------

  uv sync
  uv sync --extra dbx          # Databricks operator/local helpers
  uv sync --extra confluence   # optional blog publisher

Common environment variables (`.env` is loaded):

  DTRACK_CONFIG=/absolute/path/config.json
  DTRACK_RUN_S3=s3://bucket/dtrack/runs     # stable root; never include run_id
  DTRACK_RUN_ID=20261007T150000Z-orders     # optional; row-check can generate it
  DTRACK_LOG_LEVEL=INFO
  DTRACK_DBX_PROFILE=corp
  DTRACK_DBX_WAREHOUSE_ID=<warehouse-id>   # local/key-check only
  DTRACK_PAIRS=orders,customers
  DTRACK_DEBUG=ipdb                        # ipdb | attach

DuckDB budget (every Left/local DuckDB connection: file sources, statistics, local landing):

  DTRACK_DUCKDB_MEMORY=20GB                # example for a 32GB machine; default 60% physical RAM
  DTRACK_DUCKDB_WORKERS=2                  # parallel column shards; splits RAM and CPU evenly
  DTRACK_DUCKDB_TEMP=D:\dtrack-spill       # spill + statistics scratch; default <work-dir>/duckdb
                                           # (col-check) or <run>/_local/duckdb (local), then
                                           # <system temp>/dtrack-duckdb when that is not writable
  DTRACK_STATS_BATCH=64                    # attributes per calculation + S3 publication wave
  DTRACK_PROGRESS_INTERVAL=10              # persistent progress-log interval in seconds
  DTRACK_LEFT_LOG=/path/to/left.log        # distributed CLI override; default .dtrack-work/logs/<run>.log

Live source query profiling (Oracle, Athena, Hadoop):

  Create the ignored `tests/live/source_queries.json` described in
  `tests/live/test_source_queries.py`, then run:

    just live profile

  The performance group separates connection, execute, first/remaining fetch, DataFrame,
  CSV export/read, comparison, and cleanup time. It writes ranked JSON reports to
  `.dtrack-work/live-timings/` and prints the five slowest steps; override that directory with
  `DTRACK_LIVE_TIMINGS_DIR`. Set
  `DTRACK_LIVE_PROFILE_RUNS=3` for repeated measurements or
  `DTRACK_LIVE_PROFILE_FETCH_SIZE=10000` to compare fetch sizes. Inputs accept UTF-8 with or
  without a BOM; reports are UTF-8/LF. Paths use `pathlib` and report filenames avoid Windows
  reserved characters, so the same tests can run from Windows or Linux/Databricks.

Set DTRACK_DUCKDB_MEMORY to what the machine can really give dtrack: each connection gets
MEMORY / WORKERS and `cpu_count / WORKERS` threads, and spills to DTRACK_DUCKDB_TEMP above that
instead of failing. A 1715-column
window of 70k rows completes inside 4 GiB per connection; without a budget DuckDB assumes 80%
of RAM (on Windows including the page file) for every connection at once.

For a 32GB, 10-core machine, start Version 2 Left work with `--pull-workers 1`,
`DTRACK_DUCKDB_MEMORY=20GB`, and `DTRACK_DUCKDB_WORKERS=2`. DTrack runs one vintage at a time;
its two column shards each receive about 10GB and five DuckDB threads. `--stat-workers` remains
accepted for command compatibility but is fixed to one vintage.
Database CSV pulls stream 10,000 rows at a time; statistics still use one scratch DuckDB per
vintage and calculate/publish mapped columns in `DTRACK_STATS_BATCH` waves.

Local-only (Databricks SQL warehouse pulls through a corporate proxy):

  USERNAME / PASSWORD / AWS_HOST           # proxy http://USERNAME:PASSWORD@AWS_HOST:8080 for
                                           # presigned EXTERNAL_LINKS chunk downloads; unset ->
                                           # HTTPS_PROXY. Windows pre-sets USERNAME to the login
                                           # name, and .env never overrides a set variable.

Every option with an environment binding shows its exact variable in `--help`.

Keep passwords/tokens in environment variables or secret stores, never in shared payloads.
The Left hand-off removes credentials, DSNs, hostnames, HTTP paths, and *_env fields.
Executed SQL is intentionally retained and can contain configured predicates or fixed sample-key
literals; restrict access to each run prefix accordingly.

Command option precedence for `dtrack left-run`, `dtrack row-check`, `dtrack col-check`, and
`dtrack local` is:

  CLI > config command section > environment > built-in

Use top-level `left-run`, `row-check`, and `col-check` objects for optional arguments. For example:

  "left-run": {"run-s3": "s3://bucket/dtrack/runs", "pull-workers": 1, "force": false},
  "row-check": {"run-s3": "s3://bucket/dtrack/runs", "workers": 4, "force": false},
  "col-check": {"run-s3": "s3://bucket/dtrack/runs", "pull-workers": 2, "force": false}

Display effective defaults with:

  dtrack left-run --config config.json --help
  dtrack row-check --config config.json --help
  dtrack col-check --config config.json --help
  dtrack local run --config config.json --help


2. CONFIG
---------

Minimal pattern:

{
  "version": 2,
  "connections": {
    "ora_main": {
      "source": "oracle",
      "dsn": "host:1521/SERVICE",
      "user_env": "ORA_USER",
      "password_env": "ORA_PASSWORD"
    },
    "dbx_main": {"source": "databricks"}
  },
  "pairs": {
    "orders": {
      "left": {
        "conn_macro": "ora_main",
        "table": "APP.ORDERS",
        "date_col": "BUSINESS_DATE",
        "date_type": "date"
      },
      "right": {
        "conn_macro": "dbx_main",
        "catalog": "main",
        "schema": "sales",
        "table": "orders",
        "date_col": "business_date",
        "date_type": "date"
      },
      "fromDate": "2026-01-01",
      "toDate": "2026-01-31",
      "vintage": "month",
      "key": "ORDER_ID,LINE_ID",
      "key_families": {
        "ORDER_ID": "numeric",
        "LINE_ID": "numeric"
      },
      "sample": 0.10,
      "statistics": ["hash_sum", "n_unique"],
      "excluded_partitions": [],
      "excluded_columns": [],
      "col_map": {
        "ORDER_ID": "order_id",
        "LINE_ID": "line_id",
        "AMOUNT": "amount",
        "STATUS": "status"
      },
      "col_type_overrides": {"AMOUNT": "numeric"},
      "strict": true
    }
  }
}

Parameter choice:

  left.source
    oracle | file/csv | duckdb | athena | hadoop
    Hadoop connects through a pyodbc DSN from `left.dsn`, `left.conn_macro`, or `HADOOP_DSN`.

  left relation
    table, schema+table, or query. `query` may be inline SQL or a config-relative `.sql` file.
    `where` adds a source-side filter.

  left.nullstr
    CSV-only missing-value marker passed to DuckDB before date probing, sampling, and statistics.
    It may be one string or a list; SAS-style exports commonly use
    `"nullstr": ["", "NULL"]`. The existing `left.options.nullstr` form remains supported,
    but do not set both forms to different values. If `NULL` can also be real text, preserve a
    quoted/unquoted distinction with `options.allow_quoted_nulls`, or normalize selected columns
    in a `{src}` query instead of applying a file-wide marker.

    For a multi-view Oracle query, place a controlled predicate marker inside each dated driver:

      -- queries/consolidated.sql
      WITH driver_one AS (
        SELECT * FROM DRIVER_ONE d1 WHERE {{query_windows:driver_one}}
      ), driver_two AS (
        SELECT * FROM DRIVER_TWO d2 WHERE {{query_windows:driver_two}}
      )
      SELECT d1.BUSINESS_DT AS FINAL_DT, d1.SSN, a.STATUS
      FROM driver_one d1
      LEFT JOIN driver_two d2
        ON d1.BUSINESS_DT = d2.ACTIVITY_DT AND d1.SSN = d2.SSN
      LEFT JOIN ACCOUNT_VIEW a ON d1.ACCOUNT_ID = a.ACCOUNT_ID

      "left": {
        "conn_macro": "ora_main",
        "query": "queries/consolidated.sql",
        "date_col": "FINAL_DT",
        "date_type": "date",
        "query_windows": {
          "driver_one": {"expression": "d1.BUSINESS_DT", "date_type": "date"},
          "driver_two": {"expression": "d2.ACTIVITY_DT", "date_type": "date"}
        }
      }

    The undated account view needs no marker. Row check renders the configured inclusive
    fromDate/toDate bounds inside both drivers. Col check renders the exact admitted dates,
    preserving holes. Schema/date/key probes use `1=1`. The outer FINAL_DT predicate remains a
    guardrail, and deterministic hash sampling remains outside the final joined relation.
    Marker declarations and uses must match exactly; DTrack rejects unknown, unused, or malformed
    markers before querying Oracle. This is controlled substitution, not Python string formatting.

    The query must return every configured Left date, key, and non-excluded mapped column. Keep
    filters inside the source query; `left.where` should reference returned aliases such as the
    configured date or keys.

  right.kind
    table (default): catalog/schema/table
    query:            query
    files:            path + format; query may reference {src}

  partition_mode
    date (default): both sides require date_col and use normal date partitions/windows.
    all: date_col is optional and ignored for partitioning. DTrack creates one `all` partition,
    compares whole-relation row counts, and applies fraction/fixed sampling once across the full
    dataset. A real stable key is still required when sample is not all rows.

    `all` rejects fromDate, toDate, vintage, date_synonyms, excluded_partitions, and Left
    query_windows instead of silently ignoring them. `dtrack tools materialize` and SAS bundle
    export currently require the default date mode.

    Minimal undated Pair:

      {
        "partition_mode": "all",
        "left": {"source": "oracle", "table": "APP.ACCOUNTS"},
        "right": {"source": "databricks", "table": "main.curated.accounts"},
        "key": "ACCOUNT_ID",
        "sample": 0.1,
        "col_map": {"ACCOUNT_ID": "account_id", "BALANCE": "balance"}
      }

  date_col
    Required on both sides in partition_mode=date. It defines Stage-1 partitions and Stage-2
    windows. It may be omitted in partition_mode=all.

  date_type
    date     native DATE/TIMESTAMP values
    string   YYYY-MM-DD or YYYYMMDD text
    number   numeric YYYYMMDD
    sas      DATE9 (`31JAN2026`), SAS datetime (`01AUG2026:09:45:35`), or numeric SAS days

    Those are the only configurable names; missing defaults to `string`. Left and Right may
    differ. For `string` and `sas`, preflight selects at most 16 non-null values, requires one
    consistent physical format, caches it, and writes its internal spec to row/manifest payloads.
    Col filtering and date-key hashing then reuse that spec without probing again. If date_col is
    also a key, its Left/Right specs are inherited automatically.

    Platform SQL is isolated behind DateSqlPlatform: Left ships Oracle, Athena, Hadoop, DuckDB,
    and Spark adapters; the standalone Databricks package ships only Spark/Databricks.

  fromDate / toDate
    Inclusive Stage-1 bounds. Prefer an intentionally limited first run.

  date_synonyms
    Maps exceptional partition labels before Left/Right count comparison, for example
    {"3000-01-01": "2026-07-01"}. Do not use it to hide real data errors.

  col_map
    Left -> Right column names. Inline JSON or a config-relative CSV/JSON file.
    CSV header: left,right[,type]. The date column is excluded from value statistics.
    `type` may be numeric, categorical, or a registered attribute comparison type. Built-in
    `sas_datetime_date` compares Left `01AUG2026:09:45:35` with Right native dates as
    `2026-08-01`. JSON may use
    {"SAS_ATTRIBUTE": {"right": "date_attribute", "type": "sas_datetime_date"}}.

  key
    Record identity, comma-separated. Required when `sample` is not all rows.
    Keys should be stable and jointly identify records inside the comparison window.

  key_families
    Normalization before deterministic hashing:
      string  = trim + lowercase (default)
      exact   = trim, preserve case/zeros
      numeric = trim + remove numeric leading/trailing zeros (`007`, `+7.00` -> `7`)
      date    = canonical YYYY-MM-DD
      digits  = keep digits only
    A custom step list/object is supported, but Left Python/SQL and Right Spark semantics
    must remain identical. `CAST(... AS STRING)` inside key normalization is expected;
    it should not appear as a blanket cast of all selected value columns.

  sample
    missing|false|"" = all rows
    0 < float <= 1   = deterministic fraction by normalized composite-key MD5 bucket
    positive integer = fixed N distinct keys per vintage window; Left publishes the
                       selected key tuples in pairs/<pair>/fixed_keys.json for Right reuse

  statistics
    Optional Pair-level list of Stage-2 column metrics. Missing means the complete standard set.
    To calculate and compare only normalized hash sums and distinct-value counts, use:

      "statistics": ["hash_sum", "n_unique"]

    Supported names are n_total, n_missing, n_unique, mean, std, min, max, length_avg,
    length_max, and hash_sum. DTrack stores them in canonical order, rejects duplicates and
    unknown names, and always retains col_type as normalization/report metadata. A custom list
    also skips categorical Top-10 work; only selected metrics determine the column verdict.

  vintage
    day | week | month | quarter | year. This groups admitted matching dates; it does
    not fill missing dates and is not the job schedule. It is invalid in partition_mode=all.

  strict
    Normalizes compared text more aggressively. It does not replace key_families.

  col_type_overrides
    Mapped Left value column -> numeric|categorical. Use only when inference is wrong.

  skip
    true excludes the pair.

  large local CSV materialization
    A single CSV is scanned once per Stage-2 window, so materialize it before recurring runs:

      dtrack tools materialize --config config.json --pair orders --delete-source

    The command chooses day or month physical partitions independently of vintage, normalizes
    the configured date column to native DATE, stores deterministic `dtrack_hash`, sorts each
    partition by that hash, validates per-day total/1%/2% counts, updates config atomically, and
    only then deletes the CSV. `week`, `month`, and `year` vintages reuse the same dataset.
    `--partition day|month` overrides auto selection; `--out` overrides the sibling
    `<csv-stem>.dtrack-parquet` destination. Deletion is refused for a source with `where` or
    `query`, because that would destroy rows outside the derived view.
    Large inputs require a full probe scan, a hash-sort/compressed Parquet write, and a validation
    scan. In a terminal DuckDB shows its query-plan progress and ETA after two seconds. Redirected
    or non-interactive runs log elapsed time and bytes written every 30 seconds instead. The final
    machine-readable result remains one JSON object on stdout.


3. DISTRIBUTED CLI WORKFLOW
---------------------------

Choose one stable runs root. dtrack creates/resolves RUN_S3/RUN_ID:

  RUN_ID=20261007T150000Z-orders
  RUN_S3=s3://my-bucket/dtrack/runs
  RUN_URI=$RUN_S3/$RUN_ID

A. Validate config and Left access

  dtrack tools doctor --config config.json

`doctor` connects to Left and describes the Right relation; it does not prove the Right
Databricks source is reachable. For a both-side connection check use local preflight:

  dtrack local preflight --config config.json

B. Optional: prove sample-key parity before a long run

  dtrack local key-check --config config.json --pair orders \
    --from-date 2026-01-01 --to-date 2026-01-03

Temporary diagnostic overrides:

  dtrack local key-check --config config.json --pair orders \
    --key ORDER_ID --key LINE_ID \
    --family ORDER_ID=numeric --family LINE_ID=numeric \
    --sample 100

Exit 0 means the selected Left and Right key sets match. Artifacts default to
`.dtrack-local/keycheck/<pair>/`.

C. Start the Databricks Right notebook/Job

It may start before or after row-check; it waits for `pairs/<pair>/row_check/left.json`.

Upload the Right package, or download a Workspace tree for inspection/backup:

  dtrack tools dbx workspace upload src/dtrack_right /Users/<you>/dtrack/dtrack_right --overwrite
  dtrack tools dbx workspace download /Users/<you>/dtrack/dtrack_right ./downloaded-right

`workspace download` recursively mirrors Workspace files and notebooks, restores a source
notebook's language suffix, refuses to replace local files without `--overwrite`, and supports
`--dry-run` plus `--profile` like upload.

  run_s3      = s3://my-bucket/dtrack/runs       # stable root; no run_id
  run_id      = $RUN_ID                          # recommended: explicit
  gate        = auto | manual | ratio:<0..1>
  wait_timeout= 1800
  idle_timeout= 900

Gate selection:
  auto        release a pair when at least one date partition matches
  ratio:0.05  require a match and at most 5% excluded partitions
  manual      record findings but release no manifest; after review, use row rollback/new run
              and rerun the Right Job with auto or ratio policy to release Stage 2

For `version: 2`, the gate option does not admit partitions. Right writes its row-check JSON/CSV,
then stops immediately if any `count_diff`, `left_only`, or `right_only` partition is absent from
`excluded_partitions`. No Right statistics run before this condition is satisfied.

`examples/nbs/06_pair_progress.ipynb` writes the one-click Left script, uploads `src/dtrack_right`
plus the progress collector, creates both Jobs (Right on demand, collector every 15 minutes), the
progress tables/views, and the pair-progress AI/BI dashboard; EXECUTE=False is a full dry run.

Monitor a submitted Job (this command monitors; it does not submit the notebook):

  dtrack tools dbx runs --active --job-id <job-id>
  dtrack tools dbx runs --run-id <databricks-run-id>

D. Run Left Stage 1

All active pairs:

  dtrack row-check --config config.json --run-s3 "$RUN_S3" \
    --run-id "$RUN_ID" --workers 4

Selected pairs (`--pair` is repeatable):

  dtrack row-check --config config.json --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair orders --pair customers --workers 4

Outputs include:
  pairs/<pair>/row_check/left.json    Left counts + credential-free pair config
  _status/left_row_check.closed.json  Left Stage-1 barrier
  pairs/<pair>/row_check/result.json  Right verdicts
  report/pairs/<pair>/row_check.csv
  pairs/<pair>/plan.json              Stage-2 plan only when the gate passes
  _status/row_check.closed.json       Right Stage-1 barrier
  _status/audit.sql                   representative best-effort SQL for this run

Read-only SQL shapes use deterministic detailed audit filenames, so restarting the command does
not create another file for the same shape. For a very wide SELECT, the audit shows the first two
and last two attributes with an `attributes omitted from audit` ellipsis and no SQL hash. The full
unshortened SQL is still what Oracle executes.

Version 2 normally replaces sections D and E with one command:

  dtrack left-run --config config.json --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --workers 2 --pull-workers 1 --stat-workers 1 --wip 200

This writes the current Pair plan and all Left Units without waiting for a Right signal. If Right
later reports unexcluded mismatches, add those dates to `excluded_partitions`, optionally add
columns to `excluded_columns`, and rerun this same command with the same run id. Unchanged Units
are reused; only affected vintages/columns are pulled and published. Then restart the Right Job.

An identical rerun with the same run id also reuses the saved Left row counts. If a pull completed
but its statistics did not, the local CSV is reusable across command processes when the same
`--work-dir` contains both `left.csv` (or `left-0001.csv`, etc.) and its `.dtrack.json` sidecar.
The sidecar must match the run, Pair plan, vintage, projected columns, and sampled keys; a bare or
stale CSV is pulled again.

To deliberately repeat all Left work for the selected Pairs, add `--force`:

  dtrack left-run --config config.json --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --force --workers 2 --pull-workers 1 --stat-workers 1

Force removes the selected run's existing row/column checkpoints, Units, results, failures,
closures, fixed keys, and derived reports before rebuilding them. It does not append a second set
of active Units. `row-check --force` resets both Left stages; `col-check --force` resets only
Stage 2. With `--import-sas`, force recomputes and republishes from the already validated SAS CSVs;
it does not rerun SAS. `--force` cannot be combined with `--export-sas`.

If Oracle is reachable only from a SAS server, use the same command in two phases; there is no
additional subcommand:

  dtrack left-run --config config.json --run-id "$RUN_ID" --export-sas ./sas-run

Copy the whole `sas-run` directory to the SAS server. In `left-run.sas`, change the top-level
`dtrack_bundle` path to that copied directory and replace each `dtrack_connect_*` placeholder with
the site's normal SAS/ACCESS Oracle connection options. Run the script. Its output is:

  sas-run/request.json
  sas-run/left-run.sas
  sas-run/output/_SUCCESS.json
  sas-run/output/<pair-id>/counts.csv
  sas-run/output/<pair-id>/windows/<vintage>.csv
  sas-run/output/<pair-id>/keys/<vintage>.csv     fixed-N sampling only

After applying the configured source query/`where`, the script counts all returned partitions by
default and loops over all returned dates. `fromDate`, `toDate`, and `excluded_partitions` are the
explicit DTrack partition filters; `vintage` groups the remaining dates into output files. It
honors Pair selection, `where`, table/query and `query_windows`, mapped and excluded columns,
keys/key families, sample mode, strict mode, column types, and type overrides. Mapping changes the
Right-side names in the plan; SAS CSV headers deliberately keep the Left names. For this first
version, fixed-N sampling is limited to 1000 keys and string/SAS date types must use a concrete
format rather than auto-detection.

Copy the completed directory back without changing `request.json`, then import and upload the Left
protocol artifacts:

  dtrack left-run --config config.json --run-s3 "$RUN_S3" \
    --import-sas ./sas-run --pull-workers 1 --stat-workers 1 --wip 200

`--import-sas` reads the run id from `request.json` when `--run-id` is omitted. It verifies the
config hash, completion marker, expected vintage/key files, and ordered Left CSV headers
(case-insensitive); computes the normal statistics locally; and uploads counts, plans, fixed keys,
and Units. It does not upload the raw SAS CSVs. Start or restart the existing Right Job afterward:
Right still determines row mismatches, compares column statistics, and writes the final report.

E. Run Left Stage 2

Start this without waiting manually for Right Stage 1; it waits for
`_status/row_check.closed.json`.
The Right Job can drain units while Left continues producing them.

  dtrack col-check --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pull-workers 2 --stat-workers 1 --wip 200 \
    --wait-timeout 1800 --poll-interval 3

Selected pairs:

  dtrack col-check --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair orders --pair customers

If Stage 1 released more pairs than selected here, this is intentionally a partial Stage 2 run;
`_status/col_check.closed.json` is written only after Units for every released Pair plan exist.

Parameter choice:
  pull-workers  source query/file pulls; start 1-2 for Oracle or large extracts
  stat-workers  compatibility option fixed to one active vintage
  wip           maximum indexed-but-not-finished backlog; backpressure, not object count
  wait-timeout  maximum wait for Right Stage-1 closure
  poll-interval S3 polling interval; 2-5 seconds is usually sufficient
  work-dir      pulled window CSVs and the DuckDB scratch/spill directory (default
                .dtrack-work/col_check); put it on the disk with the most free space

When WIP backpressure is active, the log reports `ready_unclaimed`, `wip`, and `over_limit` once,
then at most once every 30 seconds until Right catches up. A final `backpressure cleared` line
reports the remaining backlog and total wait time; the old once-per-second message is not emitted.

Each window is pulled, summarized, and published before the next one; nothing accumulates in
memory across windows. Statistics load the window CSV once into a scratch DuckDB file under
work-dir (single-threaded load: the parallel CSV reader buffers every column), then run up to
DTRACK_DUCKDB_WORKERS column shards in parallel. Each shard calculates DTRACK_STATS_BATCH
attributes and immediately publishes that wave to S3, so the Right job can begin before the
vintage finishes. One tqdm bar and `left.log` show running/completed shards plus calculated and
uploaded attribute totals.

Resume: rerun the same `--run-id`. Windows whose Unit objects already exist are skipped before any
pull. A partially published window reuses its local pull only when the provenance sidecar matches,
then calculates and writes only missing Units. Use `--force` to clear Stage 2 and pull, calculate,
and publish it again.

Wide tables (hundreds to thousands of columns, 100k+ rows per window) belong in this
distributed workflow, not in `dtrack local`: the Right statistics then run on the cluster
instead of a second time on the Left machine, and the window data never crosses the proxy.

F. Reports

Reports remain under `$RUN_S3/$RUN_ID/report/`; local runs expose the same directory directly.
For S3 use the organization's standard object-store browser/sync tooling. Expected artifacts:
summary.json, `pairs/<pair>/row_check.csv`, `pairs/<pair>/col_check.csv`, index.html, and
report.xlsx.


4. PAYLOAD LAYOUT AND MONITORING
--------------------------------

<run>/
  _status/run.json                       current state/role/run/timezone
  _status/heartbeat.json                 Left producer liveness
  _status/units.csv                      human-readable Unit state snapshot
  _status/*.closed.json                  Stage barriers
  _status/audit.sql                      representative SQL without comment headers
  pairs/<pair>/plan.json                 immutable Stage-2 Pair plan
  pairs/<pair>/fixed_keys.json           fixed-N only
  pairs/<pair>/row_check/{left,result}.json
  pairs/<pair>/units/<seq>-<unit_id>.json  Left stats plus readiness metadata
  pairs/<pair>/col_check/right_ready/     durable Right Window readiness
  pairs/<pair>/col_check/results/         final comparisons
  pairs/<pair>/col_check/failures/        terminal failures + traceback
  pairs/<pair>/audit/<event>.sql          immutable representative SQL evidence
  report/pairs/<pair>/{row_check,col_check}.csv
  report/{summary.json,index.html,report.xlsx}

Why `_INDEX/` no longer exists on new runs:
  An S3 PUT is atomic for one key. Protocol v2 stores readiness metadata and Left statistics in one
  sequence-prefixed Unit JSON, so its creation is the commit. The runtime accepts protocol v2 only;
  old payload-plus-pointer runs must be completed with an older release or migrated before reuse.

Unit identity:
  deterministic SHA-256-derived id from pair + vintage window + column. Existing ids are skipped,
  and a window whose ids all exist is not pulled again, so reruns are idempotent.
  Sequence-prefixed Unit names preserve deterministic polling order.

Core monitoring invariants:
  expected = _status/col_check.closed.json.expected_units
  ready    = count(pairs/*/units/*.json)
  done     = count(pairs/*/col_check/results/*.json)
             + count(pairs/*/col_check/failures/*.json)
  backlog  = ready - done

Healthy completion:
  _status/row_check.closed.json exists
  _status/col_check.closed.json exists
  ready >= expected
  done >= expected
  failed == 0 (or every failed Unit is explicitly accepted)
  _status/run.json.state == complete

Current implementation already provides:
  paginated S3 listing; atomic single-object Unit commit;
  heartbeat timeout; WIP backpressure; deterministic unit ids; per-unit retries/dead letters;
  exact rollback target resolution; S3 deletion batches of at most 1000 objects.

SQL audit contract:
  Before a source/warehouse/Spark/DuckDB statement is submitted, dtrack fingerprints its SQL.
  The first query for each run + stage operation + pair + side + backend + SQL shape wins a lock
  and best-effort writes one immutable `pairs/<pair>/audit/<event>.sql`; repetitive vintage windows,
  multithread siblings, and retries with the same shape are not written again. A changed relation,
  projection, predicate structure, or sampling strategy creates a new shape and is retained.

  Always representative: custom relation query, preflight, partition counts, key-type probes,
  fixed-key selection, sampled window pulls, key-check, and Right statistics. Every future remote
  mutating statement is retained. Optional internal maintenance (`ATTACH`, `USE`, local landing
  CREATE/DELETE/INSERT/count, `SHOW TABLES`) is omitted by default.

  Row/col/key-check checkpoints and final completion merge SQL only into
  `_status/audit.sql`, avoiding an O(n^2) rewrite for every S3 query. Individual SQL headers contain
  only timestamp, side, backend, and operation; Pair identity comes from the path. Audit I/O failure
  never blocks the statement; writable failures stay beside the Pair audit. Detailed events are
  retained for the latest five runs; older runs keep `_status/audit.sql`. Local backup
  includes the current run's events and merged file, but never uploads `_local/`.

Industrial operating pattern for very large object counts:
  1. Keep S3 payloads immutable and authoritative; never hand-edit unit JSON in place.
  2. Emit CloudWatch metrics for expected/left-ready/complete/failed/backlog/heartbeat age and alarm on
     stale heartbeat, growing backlog, dead > 0, or closure/count mismatch.
  3. Enable S3 Inventory and query it with Athena for fleet-wide audits/search by prefix, size,
     age, and orphan status. Interactive full-prefix JSON scans are acceptable only at modest size.
  4. Maintain a secondary searchable control catalog (DynamoDB, Delta, or PostgreSQL) keyed by
     run_id/pair/window/column/unit_id/status. S3 remains truth; the catalog is an index.
  5. Use S3 Versioning plus lifecycle rules: retain reports longer, expire old units/index/results
     after the audit window, and keep noncurrent versions long enough to recover operator errors.
  6. Use this rollback planner or S3 Batch Operations for reviewed bulk deletion. Never use a
     broad recursive `aws s3 rm` against a runs root.
  7. At million-unit scale, evolve the protocol to immutable Parquet packs plus a transactional
     queue/catalog. Do not use one shared DuckDB file as the distributed multi-writer queue.

Modification rule:
  Stage-2-only change (col_map, key, key_families, sample, statistics, vintage, strict,
  type override):
    reviewed col rollback, optionally rebuild manifest with --config, then rerun col.
  Stage-1 change (left/right relation, date types, date bounds, date synonyms):
    row rollback or, preferably after unit production, a new immutable run_id.


5. ROLLBACK
-----------

Always stop/pause the Right Job first. Rollback is a dry run unless `--yes` is supplied.

One pair:

  dtrack tools rollback --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair orders --stage col

Multiple pairs:

  dtrack tools rollback --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair orders --pair customers --stage col

Comma-separated also works:

  dtrack tools rollback --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair orders,customers --stage col

Every pair discovered in the run:

  dtrack tools rollback --run-s3 "$RUN_S3" --run-id "$RUN_ID" --pair all --stage col

`--pair all` must be used alone. Unknown/typo pair names fail before any target is deleted.
Batch mode resolves all pairs first, freezes and deduplicates exact targets, then deletes.

Stages:
  dead  delete selected dead records so Right retries them
  col   delete selected Stage-2 Units/results/failures + global closure/status/final report
  row   col reset plus selected row verdict/count/Pair plan/row report + Stage-1 barriers

Any `col` or `row` rollback invalidates and deletes the run-level `report/` set, even for
one pair, because summary.json/index.html/report.xlsx describe the whole run. Restart Right to
publish a fresh set and only consume it after `_status/run.json.state` becomes `complete`.

Inspect the dry-run JSON:
  pairs, by_pair, planned, keys, targets, next

Apply exactly that logical plan (targets are resolved again at command start):

  dtrack tools rollback --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair all --stage col --yes

Stage-2 config update and manifest rebuild:

  dtrack tools rollback --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair orders --stage col \
    --config config.json --yes

Stage-1 config update and immediate Left recount in the same run:

  dtrack tools rollback --run-s3 "$RUN_S3" --run-id "$RUN_ID" \
    --pair orders --stage row \
    --config config.json --yes

`col + --config` keeps the Stage-1 left counts and pair verdict, validates every new
manifest before deleting anything, then rebuilds Stage 2. It refuses changes to
left/right source settings (including date_col and date_type), partition_mode, fromDate,
toDate, or date_synonyms so old counts cannot be paired with a new Stage-1 definition.

`row + --config` permits those Stage-1 changes. Its dry-run validates pair selection,
config serialization, and the preserved run_id without querying a source. With `--yes`
it deletes the selected pair's old Stage-1/2 artifacts and immediately reruns Left
row-check for those pairs with the supplied config and same run_id. Restart the Right
job to rebuild verdicts/manifests, then run col-check. Without `--config`, row rollback
only resets artifacts and the next step is a separate `row-check --config ...` command.
`dead + --config` is invalid because dead rollback only releases failed units.

Local run folders are accepted in place of S3 URLs:

  dtrack tools rollback --run-s3 .dtrack-local/runs --run-id <run_id> \
    --pair all --stage col


6. LOCAL EQUIVALENT
-------------------

  dtrack local preflight --config config.json
  dtrack local run --config config.json --pair orders --run-s3 "$RUN_S3"

Useful options:
  --run-id ID             resume the same local run; windows whose units are all indexed are skipped
  --out DIR               default .dtrack-local/runs
  --gate POLICY           same row gate
  --run-s3 URI            stable runs root; backup to URI/<run_id>, including report/

Local option precedence is CLI > config `local` section > environment > built-in. Running
`dtrack local run --config config.json --help` reads that config and displays the effective defaults.

Sampling always runs in each source/warehouse before transfer; full-window download followed by
local sampling is unsupported. `_local/` is never uploaded. Local col-check runs the Left producer
and Right consumer concurrently over the same directory
store. Errors go to `<run>/_local/logs/errors.log`; normal CLI JSON remains on stdout.

Reuse pulled windows without touching either source (interrupted run, statistics-only rerun):
`examples/nbs/05_reuse_pulled.ipynb` opens the existing `<out>/<run_id>` with
`open_run(..., reuse_pulled=True, land=False)` and a `WarehouseTarget(None, ..., reuse=True)`.
Left returns `_local/left/<pair>/<bucket>/left.csv`, Right computes from
`_local/right/<pair>/<bucket>/right.csv`, a missing file raises instead of pulling, dead units are
released first, and `report()` then writes `<run>/report/`. Pulls write `<name>.part` and rename, so
every CSV that exists is complete.

Right windows are pulled from the SQL warehouse with `disposition=EXTERNAL_LINKS` (the INLINE
default caps a statement result at 25 MiB) and downloaded with `requests` through the proxy in
section 1; counts and DESCRIBE stay inline. The local runner may use DuckDB for Left pulls,
statistics, Right statistics, and landing. DTRACK_DUCKDB_WORKERS is the intra-vintage shard count;
run one local run per machine. It is the fallback for small pairs; see section 3E for wide tables.
Representative submitted SQL shapes are retained in `<run>/_status/audit.sql`; key-check uses
`.dtrack-local/keycheck/<pair>/audit.txt`.

Confluence tracking pages use one grouped lifecycle:

  dtrack tools blog preview --report <report-dir>
  dtrack tools blog publish --report <report-dir> --space DTRACK
  dtrack tools blog preview \
    --template templates/confluence/business-validation-overall.xhtml \
    --data templates/confluence/business-validation-overall.example.json
  dtrack tools blog publish \
    --template templates/confluence/business-validation-overall.xhtml \
    --data validation-status.json --space DTRACK --attach evidence.xlsx
  dtrack tools blog update --page-id <id> \
    --append-table new-table.json \
    --add-evidence new-evidence.json \
    --set-status 'Orders.business_pvt=PASS' \
    --attach orders-signoff.xlsx
  dtrack tools blog inspect --page-id <id>
  dtrack tools blog delete --page-id <id>              # dry run
  dtrack tools blog delete --page-id <id> --yes        # move to trash
  dtrack tools blog delete --page-id <id> --purge --yes

`inspect` returns page metadata, versions, restrictions, and attachments. Publish also manages
attachments, version retention, and view/edit restrictions. New/updated pages default to view/edit
access for the publishing user only; use `--space-visible` to inherit normal space visibility.
Template artifacts may be web links or attachment names. The old flat `blog --publish` and
`blog-delete` commands are intentionally absent.

Template publication stores versioned structured state as a Confluence content property.
`blog update` merges tables, evidence, and statuses into that state, then redraws the exact page id;
it never appends raw XHTML. Use `Orders=PASS` for overall status and
`Orders.tech_pvt=PASS` or `Orders.business_pvt=PASS` for phase status.

For very large `source=file` CSVs, DuckDB scans the file in place and applies partition/sample
predicates before export. DTrack writes matching rows in 10,000-row batches and computes statistics
with batched DuckDB aggregates over a scratch table, so it does not materialize the whole CSV in
Python RAM. Every connection runs under the DuckDB budget in section 1 and spills to
DTRACK_DUCKDB_TEMP. Prefer partitioned Parquet for repeated runs because projection/filter
pushdown avoids reparsing the full CSV.

After `dtrack tools materialize`, fraction sampling uses the stored versioned `dtrack_hash` when
the configured keys and key families still match. If that contract changes, DTrack falls back to
recomputing the hash from the keys rather than silently reusing a stale value.

The CSV Right stand-in lives only in `dtrack_local`. The uploaded
`dtrack_right` package contains the Spark target, Spark sampling SQL, comparison, store, audit,
and report code; it does not ship local CSV execution or source-platform sampling adapters.


7. QUICK FAILURE ROUTING
------------------------

Config/load failure:
  run `dtrack tools doctor`; verify source, date_col, col_map, relation fields, and env names.

Left/right sample mismatch:
  run `dtrack local key-check`; inspect key order, col_map, key_families, nulls, dates, and zeros.

col-check waits forever:
  inspect _status/run.json, _status/row_check.closed.json, Right Job state, gate decision,
  and wait_timeout.

Large backlog:
  inspect `_status/units.csv`, `_status/heartbeat.json`, Right Job logs and Pair failures, then tune
  producer WIP or
  Right capacity from measurements. More pull/stat workers do not fix a stalled Right consumer.

Dead units:
  read pairs/<pair>/col_check/failures/<unit_id>.json and the dedicated job/local error log; fix the cause; dry-run
  `rollback --stage dead`; apply; restart the Right Job with the same run_id.

Out of Memory Error / statistics take tens of minutes per window:
  set DTRACK_DUCKDB_MEMORY to the RAM the machine can spare and DTRACK_DUCKDB_WORKERS to the
  number of parallel column shards; point DTRACK_DUCKDB_TEMP at a disk with room to spill; run one
  dtrack process per machine. Lower DTRACK_STATS_BATCH only if a single batch still exceeds the
  per-connection limit. Wide tables go through the distributed workflow (section 3E).

Local run: "inline byte limit exceeded" or presigned chunk download hangs:
  the window exceeds 25 MiB inline; dtrack already requests EXTERNAL_LINKS, so verify the proxy
  variables in section 1 (USERNAME/PASSWORD/AWS_HOST) and that the presigned storage host is
  reachable through that proxy.

Wrong config after Stage 2 started:
  preserve report/evidence, stop Right, create a new run when in doubt. A new run is safer than
  mutating an audit trail.
