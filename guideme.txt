pair_recon guide

1. Prepare

Install uv, Python 3.11+, Databricks CLI/profile access, and an ODBC driver when Hadoop is used.

  uv sync
  uv sync --extra hadoop
  copy .pair_recon.env.example .pair_recon.env        Windows
  cp .pair_recon.env.example .pair_recon.env          Linux

Workstation execution is supported only through uv run. run.cmd and run.sh are thin uv run wrappers; PairRecon does not build a standalone executable. just publish creates dist/pair_recon.zip with only the main runtime source, minimal installation files, setup/pairs.xlsx, and a compact English readme.txt.

Every PairRecon CLI, install.py, and mapping.ipynb automatically loads only .pair_recon.env; an existing process environment value wins. For Oracle, use ORACLE_USER plus ORACLE_PASSWORD or the selected macro's <MACRO>_PWD. ORACLE_SVC may map aliases such as pb30:service,pcds:service. Add ORACLE_DSN only if the selected pair does not provide a service through its macro. With LDAP naming set LDAP_DSN=ldap://host/service,cn=OracleContext,... instead: it is resolved through ldap3 to the TNS descriptor once per source, needs no service mapping, fills {service} from the macro map, and yields to an explicit dsn or a per-macro <MACRO>_LDAP_DSN. A pair may instead name custom user_env/password_env/dsn_env/ldap_dsn_env variables in left_options_json. Databricks credentials stay in ~/.databrickscfg. Hadoop uses HADOOP_DSN plus the left_conn schema and an installed ODBC driver. Local .pair_recon.yaml contains prompt defaults, never secrets. All text files and sampled CSVs are UTF-8.

The previous pkg/distributed branch used DTRACK_S3, AWS/WinSCP, DTRACK_DBX_*, and many DTRACK_* runtime controls. They are not required by the current UC Volume design. PAIR_RECON_OUTPUT_DIR optionally selects the local artifact root and defaults to outputs under the current working directory. PAIR_RECON_TIMING=true performs a bounded 120-second Oracle/Hadoop Left pull benchmark; a numeric value sets the seconds. It uses the configured sample SQL and real arraysize batches, measures at least three batches, prints execute/first-batch latency, records/s, and vintage/sample-rate projections, closes the cursor/session, and exits without Right, statistics, Volume artifacts, or status updates. DBX_PROFILE, DBX_CLUSTER_ID, DBX_WAREHOUSE_ID, DBX_WORKSPACE_PDIR, DBX_CATALOG_SCHEMA, DBX_PAIR_WORKBOOK, and DBX_RUN_PATH are the Databricks defaults.

2. Unity Catalog

Set DBX_CATALOG_SCHEMA=catalog.schema. Create or confirm all fixed PairRecon tables using setup/schema.sql, including pair_recon_normalization, then run setup/reference.sql to seed field and keyword definitions. Table names live in src/pair_recon/core/metadata/constant.py. Existing installations run setup/migrate_pair_metadata.sql, setup/migrate_run_status.sql, and setup/migrate_observability.sql once as applicable, then rerun setup/schema.sql and setup/reference.sql.

setup/pairs.xlsx has three worksheets. pairs contains the compact source metadata and run defaults. pair_sql contains optional SQL/query-window JSON, joined by pair_name. field_guide gives a short definition and example for every field. install.py upserts pair_meta and pair_sql without deleting omitted pairs or overwriting latest_run_id/latest_status. When DBX_PAIR_WORKBOOK exists, it is compared with both UC tables before pair selection and changed or new rows are upserted. Remote pairs omitted from the workbook are not deleted. setup/setup.sql remains a manual SQL example and repair reference.

In pairs, left_conn is the Oracle macro, Hadoop schema, or CSV path. right_conn is catalog.schema for databricks_table, a file path for databricks_files/CSV, and blank for databricks_query. left_table/right_table are filled only for table sources. vintage is a dedicated field. Put uncommon source settings in left_options_json/right_options_json. Put prompt defaults in run_defaults_json, normally using a sample fraction such as {"sample":0.1}; sampled runs require key_columns, each as NAME[type] (numeric, categorical, or a registry name such as string, exact, date, digits, date_type, sas_datetime_date); the type overrides the key's column-map data_type and the sync writes it there. Keys never come from the prompt. run_defaults_json accepts run_mode, checks, sample, audit, sync_remote, left_workers, right_workers, vintage, from_date, to_date (YYYY-MM-DD), excluded_partitions, excluded_columns (mapped Left names skipped by the column check, case-insensitive; the Excluded columns prompt edits the same list), sample_rows (default 50), vintage_sample_size, vintage_values, and a data_type object such as {"AMOUNT":"numeric","ORDER_DT":"date"}. During every workbook sync, data_type updates those Left columns in pair_recon_column_map, preserves an existing right_column, and uses the same column name when no mapping exists. The configured left_date_col is always created or updated to map to right_date_col while preserving its existing data_type. checks, excluded_partitions, excluded_columns, and vintage_values may be JSON arrays or comma-separated strings; PairRecon trims, removes blanks, de-duplicates, and stores arrays. For dated CLI runs, an absent or blank effective to_date defaults to the current day in the selected run timezone, including that day; explicit end dates retain the existing precedence. Date-only fields are rejected in all mode. Saved answers for the same pair in .pair_recon.yaml still win over these defaults. Relative CSV paths use the current working directory. Date types are auto-detected unless a side option overrides them.

Put one row per mapped Left attribute in pair_recon_column_map:

  INSERT INTO catalog.schema.pair_recon_column_map VALUES
    ('orders', 'AMOUNT',    'amount',     'numeric'),
    ('orders', 'SAS_DT',    'event_date', 'sas_datetime_date'),
    ('orders', 'POSTED_AT', 'posted_at',  '{"type":"date","left_date_type":"date","right_date_type":"date"}');

data_type may be blank, numeric, categorical, a registered normalizer name (string, exact, date, digits, date_type, sas_datetime_date), a JSON step list, or a JSON object with type/left_date_type/right_date_type or transform/left_transform/right_transform. Key columns reuse the same data_type for sampling normalization; the partition date key uses right_date_col and the pair-level date types when its row has no data_type. An explicit Right date_type (and the right_date_type of a date data_type) must fit the physical column: string/number/sas on a date or timestamp column, or date on a text column, fails the Right health check instead of raising a Databricks CAST_INVALID_INPUT or parsing to NULL. Mapping rows define the effective column map and type overrides. config_json is only a generated snapshot; explicit pair_meta columns are authoritative.

Normalization is controlled only by enabled rows in pair_recon_normalization and is not asked in the prompt. Its five columns are rule_name, source, match_value, canonical_value, and enabled. A blank match_value means a supported transform; otherwise the row is a source-scoped synonym. To add a transform, define a NormalizationRule subclass with normalize_value(text) and normalize_sql(expr, dialect), decorate it with @register_rule, and mirror it in both hashing.py modules. Registered names are accepted automatically; enable the transform through its normalization-table row. Configured rule order is preserved. source=all applies everywhere; @missing and @run_date are special canonical values. setup/schema.sql seeds trim, strip_quotes, lowercase, decimal, strip_datetime, Oracle 3000-01-01 to @run_date, and Oracle 9999-12-31 to @missing as enabled while preserving later enabled choices. strip_quotes removes repeated or mixed single/double quotes at text edges and preserves interior quotes. Existing installations can enable it with setup/migrate_strip_quotes.sql after deploying both updated sides. strip_datetime reduces ISO datetime text to YYYY-MM-DD on both Left and Right. The effective enabled rules are saved in .pair_recon.yaml, request.json, the merged config, and config/manifest.json. Use mapping data_type=date when a specific column needs explicit date parsing independently of this system transform.

Put at most one row per pair in pair_recon_pair_sql:

  INSERT INTO catalog.schema.pair_recon_pair_sql
    (pair_name, left_sql, left_query_windows_json, right_sql, right_query_windows_json)
  VALUES
    ('orders',
     'SELECT * FROM left_orders l WHERE {{query_windows:driver}}',
     '{"driver":{"expression":"l.BUSINESS_DT"}}',
     'SELECT * FROM right_orders r WHERE {{query_windows:driver}}',
     '{"driver":{"expression":"r.business_dt"}}');

Non-blank SQL replaces that side's table relation; blank SQL uses the configured table. Set right_source=databricks_query for a SQL-only Right. Keep marker declarations beside their SQL in left_query_windows_json/right_query_windows_json. Metadata/health check renders markers as 1=1, row checks use the requested bounds, and attribute checks use the exact admitted dates.

Row check always covers the complete requested range. Attribute rows normally use a percentage sample: set sample to a fraction in run_defaults_json or at the prompt. The hash sample is deterministic for the configured key_columns. Optional vintage_values or vintage_sample_size in run_defaults_json may narrow the date buckets; never set both. A random vintage_sample_size skips buckets that earlier runs of the same pair and vintage already finished (pair_recon_window_history), so daily runs cover the remaining buckets; the log prints vintage coverage. When every bucket is covered the run fails with coverage N/N until --recheck or explicit vintage_values is used. A window counts as finished only when every column has a Right result and all its partitions matched on row count.

Hadoop reads its schema from left_conn and its DSN from HADOOP_DSN. The prompt asks only for an optional schema override. A query-only Hadoop definition is also valid. CSV accepts nullstr, date_format, and DuckDB read_csv options. Use forward slashes or a quoted Windows path. Right metadata remains Databricks, but the run prompt may replace it with a local CSV. One execution handles one pair. Different owners remain isolated because owner is part of the daily run_id.

3. One-time remote setup

  ./setup/setup.sh
  setup\setup.cmd

The installer uploads and mirrors Right code, upserts the job, then refreshes pair_meta and pair_sql from setup/pairs.xlsx. Use --skip-config only for a code/job-only deployment. Record the Right job id when Right uses Databricks. A local Right CSV does not start this job. Both paths need UC metadata/results tables and the UC Volume.

To build column mappings from live schemas, run:

  uv run --with jupyterlab jupyter lab setup/mapping.ipynb

PROFILE, WAREHOUSE_ID, and CATALOG_SCHEMA default from .pair_recon.env. Set PAIR_NAME in the notebook. It derives the fixed pair and mapping table names, queries Oracle and Databricks through PairRecon src functions, previews exact/case-insensitive/normalized matches, and leaves unmatched or ambiguous columns unapplied. Review approved, set any data_type overrides, then set APPLY = True to upsert pair_recon_column_map.

Databricks operator commands use ~/.databrickscfg and may reuse these .pair_recon.env defaults:

  DBX_PROFILE=corp
  DBX_CLUSTER_ID=...
  DBX_WAREHOUSE_ID=...
  DBX_WORKSPACE_PDIR=pair_recon_app
  DBX_CATALOG_SCHEMA=catalog.schema
  DBX_RUN_PATH=/Volumes/catalog/schema/volume/runs

  just dbx login --no-open
  just dbx workspace upload src/pair_recon_right pair_recon_right --dry-run
  just dbx workspace download pair_recon_right downloaded-right
  just dbx workspace delete obsolete.py --dry-run
  just dbx workspace delete -rf obsolete-folder
  just dbx compute status
  just dbx compute start --wait
  just dbx warehouse status
  just dbx warehouse start --wait
  just dbx sql "SELECT current_user()"
  just dbx runs --limit 10

Relative Workspace paths resolve below /Users/<current-user>/; absolute paths remain supported. Remove --dry-run only after checking planned paths. Add --overwrite only when replacement is intended. delete accepts multiple paths, -r/--recursive, -f/--force, and the rm alias. Workspace notebooks regain their language suffix when downloaded. The setup installer and Sync remote mirror pair_recon_right and create pair_recon_right_job beside it. The job notebook first installs the uploaded package folder's requirements.txt through its rendered absolute /Workspace path, then calls dbutils.library.restartPython(), then uses normal package imports. Add Right-only packages such as openpyxl>=3.1 to src/pair_recon_right/requirements.txt. DBX_PKG_RENAME=pair_recon_right -> pair_recon uploads the folder as pair_recon (notebook pair_recon_job) and rewrites only the notebook's pair_recon_right imports. Remote package objects missing locally are removed only after all uploads succeed.

GitLab snapshots require authenticated glab and git:

  just gitlab create pair-validation --group GROUP
  just gitlab plan --scope left
  just gitlab plan --scope right
  just gitlab plan --scope both
  just gitlab dispatch GROUP/pair-validation --scope both --dry-run
  just gitlab dispatch GROUP/pair-validation --scope both

create always requests a private project. left and right select only that side plus shared tests. both adds the local orchestrator and setup but excludes DBX by default. all walks everything not excluded by pair_recon.ignore. This file, not .gitignore, controls the snapshot; use forward-slash patterns and no ! negation. Credentials, private keys, local defaults, and .git are always excluded. Dispatch records controlled files in .pair_recon-dispatch.json, removes only obsolete files from an earlier dispatch, preserves unrelated repository files, makes a normal commit, and never force-pushes.

4. Run

  just run
  ./run.sh
  run.cmd

  just run --defaults                         no prompts; uses .pair_recon.yaml
  just run --defaults path/to/run.yaml        no prompts; uses the named YAML
  just run --defaults --force                 auto-exclude/retry and ignore PairRecon caches
  just run --defaults --earlystop             report mismatch errors without retrying
  just run --defaults --recheck               ignore window history when sampling vintages

--defaults runs without prompts and optionally accepts a YAML path. Automatic mismatch recovery adds reported YYYY-MM-DD values to excluded_partitions, saves YAML/request.json, and restarts the same run ID, with at most three retries. --earlystop disables that recovery and reports the error directly. --force clears the run's Volume/status/error/progress results and bypasses PairRecon row/pull caches. Regardless of the flags, a failed or cancelled Right job stops the Left within seconds: running Oracle/Hadoop/DuckDB statements are cancelled and in-flight pulls are abandoned. Left column pulls wait for the Right row-check result, so unexcluded mismatches are reported before any long pull starts. Resume keeps the Left row counts and only rebuilds the plan; a plan with no windows fails at once instead of starting the Right job. There is no fixed deadline anywhere: the Right job starts after the Left row count is published, both sides wait on each other for as long as the peer is alive, and the launcher follows the job in one-hour chunks. The Left heartbeat is written during the row count, every wait, and every pull; a Left heartbeat older than ten minutes stops the Right, a failed or cancelled Right stops the Left. --recheck ignores pair_recon_window_history when choosing random vintages.

Each ordinary terminal prompt preloads its displayed .pair_recon.yaml default into an editable buffer. Press Enter to retain it, edit or delete it directly, or type undo to return to the previous question. Owner defaults to the USERNAME environment variable and falls back to the saved value only when USERNAME is unavailable. Before pair selection, an existing configured Excel workbook is compared with pair_meta and pair_sql; changed or new rows are upserted and then reloaded from UC. Confirm owner, profile, warehouse, one catalog.schema namespace, Volume, optional Outlook recipients, pair, run mode, timezone, checks, and range. The sampled key and each side's date column/type come from Pair metadata; they are printed and saved to YAML without another prompt. Date mode still asks for excluded partitions, vintage, and vintage sample. The enabled normalization-rule list is loaded from UC and recorded but is not a prompt choice. Vintage sample accepts all, a positive count such as 5, or comma-separated YYYY-MM-DD values. A Databricks job ID or exact job name is asked only for a Databricks Right. Oracle versus Hadoop and both input locations come from Pair metadata rather than duplicate run choices. left-only mode never starts Databricks Right or local CSV Right: it uses the Left definition, vintage selection, sample, checks, and column mapping to publish Left artifacts. Checks retain the checkbox loop: every input redraws the [x]/[ ] list, names or numbers toggle selections, and Enter confirms. SAS request.yaml restores exact partition/range/sample defaults. Run now is always last and both yes and no overwrite the YAML defaults. PairRecon generates `<pair>-<owner>-YYYYMMDD` in the configured timezone and replaces the same day's Volume/status/error/progress data when that ID already exists.

After a run, query pair_recon_run_error for detailed findings. Column-statistic rows use column_name for the Left column, vintage for the bucket, check_name for the failed statistic, left_value/right_value for compared values, and payload for the complete result including the mapped Right column and all match/difference fields. Row-count rows use check_name=row_count plus partition_value. Runtime failures use check_name=runtime plus detail. A successful left-only run has no findings and ends with state left_complete rather than passed. pair_recon_run_status also stores from_date, to_date, vintage, sample_rate, and vintage_sample with the summary counts. pair_recon_progress_snapshot.payload contains the complete expandable snapshot. pair_recon_reference explains observability fields and keyword values. The Right notebook publishes success/difference summaries; the local launcher only forwards failed/cancelled Jobs API details and does not download Volume result JSON. pair_recon_pair_meta.latest_run_id/latest_status points to the latest outcome. A full run is passed or different only when every planned unit has a Right result; a runtime failure leaves it incomplete. pair_recon_window_history keeps one row per finished vintage window with its result and counts; a run replaces its own rows when it republishes.

After Run now is confirmed, the local output root is created if needed and outputs/YYYY-MM-DD/<run_id>/request.json is written atomically by default before execution. Answering no saves YAML but does not create request.json or start a run. Set PAIR_RECON_OUTPUT_DIR to change that root; relative values use the current working directory. The same run directory contains left.log, DuckDB temporary state, pulled Left CSVs, fixed-key CSVs, and metadata. Input CSVs remain at their original paths. request.json contains the current prompt settings, raw pair/mapping/SQL metadata pulled from Catalog, and the merged effective config. Credential fields are removed. SQL text is retained verbatim in .txt audit artifacts, so never embed credentials in SQL.

The Right notebook logs at INFO to stdout, so its progress appears live in the Databricks job run page and in the cluster driver logs; a daemon thread also rewrites the buffered log to _protocol/right.log on the Volume every 30 seconds (20 MB cap, failed writes retried next flush), and after the Right job ends PairRecon copies it to right.log next to left.log. When the Right job fails, PairRecon fetches the task's error and Python traceback through the Jobs run-output API and writes them with the run page URL into the error and left.log. On success, the notebook returns its outcome counts through dbutils.notebook.exit and they are merged into the result's right section.

The Volume run directory contains config/ (manifest.json, mapping.csv, optional sampled_keys.json), results/ (row.json, units.csv, report/index.html, report/report.xlsx, report/differences/), and audit/. Internal resumable distributed state lives under _protocol/. Difference samples are flat CSVs at results/report/differences/diff_<attribute>.csv, one file per statistically differing attribute allowed by sample_columns. Each CSV has keys, the raw Left value, two blank spacer columns, and the raw Right value, without status or summary rows. Rows are filtered for that attribute, sorted by normalized key, and limited by sample_rows (default 50 per attribute). Only the first differing vintage is used; run_defaults_json.sample_partitions can specify an ordered preference list of vintage IDs instead. Left reuses its existing local left.csv; it is loaded and normalized once and joined once with the temporary Right slice, then each attribute is filtered independently. Right queries the sampled rows of the selected differing columns again and streams them into a temporary gzip CSV. The temporary slice is deleted after successful publication. With --keepcsv, raw left.csv, right.csv, and sample.json are preserved beside the difference CSVs; sample.json identifies the selected vintage. Use dtype=str and keep_default_na=False when reading the raw CSVs with pandas.

left-only uploads full-range row counts to _protocol/row/left.json; sample affects attribute statistics, not those counts. Column checks also publish config/manifest.json, config/mapping.csv, optional config/sampled_keys.json, and shard-batched left_statistics under _protocol/units/. Each logical unit still represents one vintage and mapped Left column. _protocol/left.json records col_check_closed when all planned Left units are ready. Progress units_ready counts logical units; units_complete counts Right comparisons and therefore remains zero. Row-check partitions and the Row Check sheet in results/report/report.xlsx use result with match, count_diff, left_only, or right_only. Snapshot pairs cannot use left-only because their comparison vintage is selected from Right row counts.

STATS_WORKERS controls concurrent local statistics shards (default 2), and PAIR_RECON_STATS_BATCH controls columns per shard (default 64); pull_workers in .pair_recon.yaml controls source pulls. progress_interval controls how often the current progress row is refreshed. Query pair_recon_progress_snapshot by run_id for state, ready/completed/failed units, and expand payload for the complete run/Left/Right/thread snapshot.

pair_recon smoke --defaults .pair_recon.yaml is the pre-flight for the saved pair: Left health check, 100 sampled rows with the real predicate, a Volume round trip, and a short Right job (smoke=1) that writes _protocol/right.json and counts how many of those keys its own predicate selects. Verdict ok, left_empty, or sample_mismatch; exit code 1 unless ok. pair_recon batch PAIR... runs pairs one by one, classifies by return code, and writes batch_summary.json. An empty plan ends as empty, left_only, or right_only once both row counts exist. Oracle sessions per source are capped by ORACLE_MAX_SESSIONS (4); ORA-02391 retries after ORACLE_SESSION_COOLDOWN_SECONDS (30) up to ORACLE_SESSION_RETRIES (3) times. The stage watchdog thresholds are FETCH_STALL_SECONDS (1800), RIGHT_FIRST_RESULT_SECONDS (14400), RIGHT_STATE_STALL_SECONDS (7200), and VOLUME_READ_FAILURES (10); 0 disables one. When it fires, both sides are cancelled and the Volume checkpoints stay for a resume. Right window statistics run in Spark by default, RIGHT_STATS_COLUMNS (50) attributes per batch, collecting one aggregate row per batch. Statistics batches reuse the sampled window's MEMORY_AND_DISK cached temp view instead of issuing a fresh source-table query per batch. Independent row counts and recomputation of lost cache partitions can still read the source. RIGHT_STATS_DRIVER_ROWS defaults to 0; setting a positive cap explicitly enables the optional pandas path, with RIGHT_STATS_DRIVER_CELLS (5000000) and RIGHT_DRIVER_FETCHES (1). Stage starts and completions are logged. The shared stdout line refreshes the active stage, batch, and elapsed time while queries run; a compact status is also logged every 30 seconds. Rendering in place depends on the output interface. Optional pandas logs separate slot waiting, SQL/toPandas, and local statistics time. Actual columns-done progress goes to _protocol/right.json after each completed batch. A state file read while the other side is overwriting it is retried on both sides.

5. Optional SAS sampling

For the integrated two-round Left flow, configure the path once in the existing field:

  left_options_json={"sas_sample_csv":"C:/PairRecon/samples/orders/left_sample.csv"}

Round 1 uses run_mode=left-only. PairRecon first performs the normal full-source Left row check and selects all requested vintage windows. If the configured CSV is missing or stale, it writes left_sample.sql and left_sample.request.yaml beside the CSV, records awaiting_sample, and does not start Right. The SQL is native Oracle SQL for an Oracle pair or native Hadoop SQL for a Hadoop pair. Use it unchanged inside the existing SAS connection-to-oracle or connection-to-odbc pass-through block and export the result to the exact configured CSV path. One SQL execution produces one CSV containing every selected vintage; retain the date column and __pair_recon_request_id column.

Round 2 changes only run_mode to full. PairRecon validates the CSV header and request ID, reuses the completed row-check checkpoint, splits the combined CSV into disjoint vintage windows internally, and uses it only for Left column/statistic pulls. The total derived slice data is approximately one additional copy of the combined rows, not one full copy per vintage. After a successful completed run and difference-sample publication, PairRecon removes the temporary left.csv slices and cache metadata but keeps the combined SAS CSV, SQL, and request. Failed or interrupted runs retain temporary slices for resume. Missing or stale output returns to awaiting_sample instead of silently querying the live Left source.

The standalone bundle command remains available when an ad hoc SAS script is preferred:

  just sas                              creates/updates left.sas only
  just sas side=right                   creates/updates right.sas only
  just sas side=both                    creates/updates both scripts
  just sas rate=0.01 bundle=work/sas

Without bundle=..., SAS uses outputs/sas or ${PAIR_RECON_OUTPUT_DIR}/sas and creates it when needed. Separate runs preserve the other script and any sampled CSV already present. Set PAIR_RECON_CONNECTION to SAS connection options for the side being run, then run left.sas and/or right.sas manually. The expected files are left_sample.csv and right_sample.csv in the bundle. Scripts contain no credentials.

After SAS writes one or both CSVs, start the normal tool:

  run.cmd
  just run

Keep request.yaml beside the CSVs for the standalone bundle flow. The integrated sas_sample_csv flow does not change the pair source to CSV and does not require an input prompt.

6. Debug and email

Normal commands do not enter a debugger. Use console or VS Code attach only when needed:

  just run --debug console
  just run --debug attach
  just sas --debug attach
  just dbx --debug attach compute status
  just gitlab --debug attach plan --scope both
  just test --debug attach

Console enters ipdb post-mortem at the original exception frame. Attach listens on 0.0.0.0:5678 and waits for a VS Code debugpy attach configuration using localhost:5678. A bare --debug still selects console. Lint --debug emits verbose diagnostics. On Windows, a configured Outlook recipient uses the signed-in Outlook desktop profile and attaches left.log.

7. Common failures

- pyodbc missing: run uv sync --extra hadoop.
- Hadoop DSN not found: create the same-bit hive ODBC DSN/driver or update HADOOP_DSN; the run prompt needs only schema.
- Oracle connection fails: verify user/password/DSN variables without printing secrets.
- CSV missing or mojibake: use an existing local path and save UTF-8; verify delimiter/read_csv options.
- Databricks 403/not found: verify profile, warehouse/job ids, UC grants, Volume path, and cluster access.
- Workspace upload/download/delete failure: run with --dry-run, verify the absolute or user-home-relative Workspace path, and check Workspace permissions; symbolic links are rejected.
- DBX id missing: set DBX_CLUSTER_ID or DBX_WAREHOUSE_ID in .pair_recon.env, or pass the matching option.
- glab missing or unauthorized: install glab, run glab auth login, and confirm GITLAB_HOST for self-managed GitLab.
- GitLab snapshot has unexpected files: run plan first, then update pair_recon.ignore; .gitignore does not control dispatch.
- GitLab push rejected: confirm repository membership, SSH/HTTPS Git credentials, branch rules, and that another user did not update the branch first.
- Progress table errors: apply the latest schema and confirm INSERT/DELETE permission.
- Right stopped with "left heartbeat is stale": the Left process died or lost Volume access for more than ten minutes; rerun the same command to resume. For CSV Right, verify its local path and headers.
- SAS connection error: set PAIR_RECON_CONNECTION separately for Oracle/ODBC and inspect the generated SQL.
- Sample CSV mismatch: preserve key/mapped headers, keep request.yaml beside the CSV, and confirm both sides use its mode/range/rate.
- Outlook failure: use Windows desktop Outlook with a signed-in profile; non-Windows runs skip mail unless recipients are empty.
- Debug attach waits forever: attach VS Code to localhost:5678, or stop the command and rerun without --debug.

8. Verify

  just test
  just lint

Live tests are opt-in. Do not run just live unless real source credentials and network access are intended.
