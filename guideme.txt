pair_recon guide

1. Prepare

Install uv, Python 3.11+, Databricks CLI/profile access, and an ODBC driver when Hadoop is used.

  uv sync
  uv sync --extra hadoop
  copy .pair_recon.env.example .pair_recon.env        Windows
  cp .pair_recon.env.example .pair_recon.env          Linux

For the normal UC-driven Oracle run, .pair_recon.env needs only ORACLE_USER and ORACLE_PASSWORD. Add ORACLE_DSN only if the selected pair does not provide left.service or left.dsn. A pair may instead name custom user_env/password_env/dsn_env variables. Databricks credentials stay in ~/.databrickscfg. Hadoop uses the non-secret left.dsn metadata plus an installed ODBC driver. Local .pair_recon.yaml contains prompt defaults, never secrets. All text files and sampled CSVs are UTF-8.

The previous pkg/distributed branch used DTRACK_S3, AWS/WinSCP, DTRACK_DBX_*, and many DTRACK_* runtime controls. They are not required by the current UC Volume design. PAIR_RECON_DBX_*, GITLAB_HOST, HADOOP_DSN, PAIR_RECON_DUCKDB_*, PAIR_RECON_STATS_BATCH, and PAIR_RECON_ORACLE_MACROS remain optional compatibility or operator overrides and do not belong in the minimal .pair_recon.env.

2. Unity Catalog

Create or confirm pair_recon_pair_meta, pair_recon_column_map, pair_recon_pair_sql, pair_recon_run_status, pair_recon_run_error, and pair_recon_progress_snapshot using setup/schema.sql. For an existing pair_recon_pair_sql created before vintage selection, run setup/migrate_pair_sql_vintages.sql once. The two companion metadata tables are read from the same catalog/schema as pair_recon_pair_meta. Pair metadata config_json selects one Left source:

  Oracle: {"source":"oracle","table":"L","service":"host:1521/service"}
  Hadoop: {"source":"hadoop","dsn":"hive","schema":"risk","table":"L"}
  CSV:    {"source":"csv","path":"C:/data/left.csv"}

Put one row per mapped Left attribute in pair_recon_column_map:

  INSERT INTO catalog.schema.pair_recon_column_map VALUES
    ('orders', 'AMOUNT',    'amount',     'numeric'),
    ('orders', 'SAS_DT',    'event_date', 'sas_datetime_date'),
    ('orders', 'POSTED_AT', 'posted_at',  '{"type":"date","left_date_type":"timestamp","right_date_type":"date"}');

data_type may be blank, numeric, categorical, a registered type name, or a custom JSON type. When mapping rows exist for a pair, they replace col_map, col_type_overrides, and column_types from config_json.

Put at most one row per pair in pair_recon_pair_sql:

  INSERT INTO catalog.schema.pair_recon_pair_sql
    (pair_name, left_sql, right_sql, vintage_sample_size, vintage_values)
  VALUES
    ('orders',
     'SELECT * FROM left_orders l WHERE {{query_windows:driver}}',
     'SELECT * FROM right_orders r WHERE {{query_windows:driver}}',
     3,
     NULL);

Non-blank SQL replaces that side's table relation; blank SQL uses the configured table. A SQL-only Right definition uses "kind":"query". Keep each marker declaration in config_json under the matching side, for example "query_windows":{"driver":{"expression":"l.BUSINESS_DT","date_type":"date"}} on Left and the corresponding r expression on Right. Metadata/preflight renders markers as 1=1, row checks use the requested bounds, and attribute checks use the exact admitted dates.

Row check always covers the complete requested range. Attribute checks use all vintage buckets when vintage_sample_size and vintage_values are NULL. Set vintage_sample_size to a positive integer for a deterministic random subset. The same run_id selects the same buckets on resume; a new run_id may select different buckets. For exact buckets set vintage_sample_size to NULL and use, for example, array('2026-01-01', '2026-04-01') in vintage_values. Values normalize to the chosen day/week/month/quarter/year bucket. Never set both fields; an unavailable explicit bucket fails closed.

Hadoop reads left.dsn from UC metadata; HADOOP_DSN remains an optional fallback. The prompt asks only for schema and reuses the pair table and DSN. A query-only Hadoop definition is also valid. CSV accepts nullstr, date_format, and DuckDB read_csv options. Use forward slashes or a quoted Windows path. Right metadata remains Databricks, but the run prompt may replace it with a local CSV. One execution handles one pair; concurrent run_ids may handle the same pair safely.

3. One-time remote setup

  ./setup/setup.sh --profile corp --workspace-dir /Workspace/Users/name/pair_recon --cluster-id CLUSTER_ID
  setup\setup.cmd --profile corp --workspace-dir /Workspace/Users/name/pair_recon --cluster-id CLUSTER_ID

Record the Right job id when Right uses Databricks. A local Right CSV does not start this job. Both paths need UC metadata/results tables and the UC Volume.

Databricks operator commands use ~/.databrickscfg and may reuse these .pair_recon.env defaults:

  PAIR_RECON_DBX_PROFILE=corp
  PAIR_RECON_DBX_CLUSTER_ID=...
  PAIR_RECON_DBX_WAREHOUSE_ID=...

  just dbx login --no-open
  just dbx workspace upload src/pair_recon_right /Workspace/Users/name/pair_recon_right --dry-run
  just dbx workspace download /Workspace/Users/name/pair_recon_right downloaded-right
  just dbx compute status
  just dbx compute start --wait
  just dbx warehouse status
  just dbx warehouse start --wait
  just dbx sql "SELECT current_user()"
  just dbx runs --limit 10

Remove --dry-run only after checking planned Workspace paths. Add --overwrite only when replacement is intended. Workspace notebooks regain their language suffix when downloaded.

GitLab snapshots require authenticated glab and git:

  just gitlab create pair-validation --group GROUP
  just gitlab plan --scope left
  just gitlab plan --scope right
  just gitlab plan --scope both
  just gitlab dispatch GROUP/pair-validation --scope both --dry-run
  just gitlab dispatch GROUP/pair-validation --scope both

create always requests a private project. left and right select only that side plus shared tests. both adds the local orchestrator and setup but excludes DBX by default. all walks everything not excluded by pair_recon.ignore. This file, not .gitignore, controls the snapshot; use forward-slash patterns and no ! negation. Credentials, private keys, local defaults, and .git are always excluded. Dispatch records controlled files in .pair_recon-dispatch.json, removes only obsolete files from an earlier dispatch, preserves unrelated repository files, makes a normal commit, and never force-pushes.

4. Run

  just run
  ./run.sh
  run.cmd

Prompts reuse .pair_recon.yaml defaults when Enter is pressed. Confirm owner, profile, warehouse, the pair/status/error/progress tables, Volume, optional Outlook recipients, pair, Left input, Right input, timezone, checks, range, run_id, and action. The check prompt lists row_count plus every registered AttributeCheck as [x]/[ ]; enter comma-separated names or numbers to toggle several, then press Enter to confirm. Left supports catalog, hadoop, or csv. Right supports catalog or csv; Right job id is asked only for catalog. SAS request.yaml restores exact partition/range/sample defaults. Resume keeps successful artifacts and retries failed/different work. Restart clears only that run_id.

After Run now is confirmed, .pair_recon-work/<run_id>/request.json is written atomically before execution. It contains the current prompt settings, raw pair/mapping/SQL metadata pulled from Catalog, and the merged effective config. Credential fields are removed. SQL text is retained verbatim for audit, so never embed credentials in SQL. Keep this file with left.log when auditing or backing up a run.

Optional PAIR_RECON_DUCKDB_WORKERS controls local statistics threads; pull_workers in .pair_recon.yaml controls source pulls. progress_interval controls seconds between progress rows. Query pair_recon_progress_snapshot by run_id for state, ready/completed/failed units, and active pair_recon thread names.

5. Optional SAS sampling

  just sas                              creates/updates left.sas only
  just sas side=right                   creates/updates right.sas only
  just sas side=both                    creates/updates both scripts
  just sas rate=0.01 bundle=work/sas

Separate runs preserve the other script and any sampled CSV already present. Set PAIR_RECON_CONNECTION to SAS connection options for the side being run, then run left.sas and/or right.sas manually. The expected files are left_sample.csv and right_sample.csv in the bundle. Scripts contain no credentials.

After SAS writes one or both CSVs, start the normal tool:

  run.cmd
  just run

Keep request.yaml beside the CSVs. Choose Left input=csv for left_sample.csv and Right input=csv for right_sample.csv. Either side may stay on its catalog source. When Right is CSV, the normal run compares locally without starting Databricks Right; UC status, errors, progress, artifacts, multithread statistics, and Outlook remain active. If request.yaml was moved, enter the exact SAS mode/range/rate manually. There is no csv-run command.

6. Debug and email

Normal commands do not enter a debugger. Use ipdb or VS Code attach only when needed:

  just run --debug ipdb
  just run --debug attach
  just sas --debug attach
  just dbx --debug attach compute status
  just gitlab --debug attach plan --scope both
  just test --debug attach

Attach listens on 0.0.0.0:5678 and waits for a VS Code debugpy attach configuration using localhost:5678. A bare --debug still selects ipdb. Lint/build --debug emits verbose diagnostics. On Windows, a configured Outlook recipient uses the signed-in Outlook desktop profile and attaches left.log.

7. Common failures

- pyodbc missing: run uv sync --extra hadoop.
- Hadoop DSN not found: create the same-bit hive ODBC DSN/driver or update HADOOP_DSN; the run prompt needs only schema.
- Oracle connection fails: verify user/password/DSN variables without printing secrets.
- CSV missing or mojibake: use an existing local path and save UTF-8; verify delimiter/read_csv options.
- Databricks 403/not found: verify profile, warehouse/job ids, UC grants, Volume path, and cluster access.
- Workspace upload/download failure: run with --dry-run, use an absolute remote path, and check Workspace permissions; symbolic links are rejected.
- DBX id missing: set PAIR_RECON_DBX_CLUSTER_ID or PAIR_RECON_DBX_WAREHOUSE_ID, or pass the matching option.
- glab missing or unauthorized: install glab, run glab auth login, and confirm GITLAB_HOST for self-managed GitLab.
- GitLab snapshot has unexpected files: run plan first, then update pair_recon.ignore; .gitignore does not control dispatch.
- GitLab push rejected: confirm repository membership, SSH/HTTPS Git credentials, branch rules, and that another user did not update the branch first.
- Progress table errors: apply the latest schema and confirm INSERT/DELETE permission.
- Right timeout: for catalog Right, verify job state, Volume visibility, and cluster access; for CSV Right, verify its local path and headers.
- SAS connection error: set PAIR_RECON_CONNECTION separately for Oracle/ODBC and inspect the generated SQL.
- Sample CSV mismatch: preserve key/mapped headers, keep request.yaml beside the CSV, and confirm both sides use its mode/range/rate.
- Outlook failure: use Windows desktop Outlook with a signed-in profile; non-Windows runs skip mail unless recipients are empty.
- Debug attach waits forever: attach VS Code to localhost:5678, or stop the command and rerun without --debug.

8. Verify

  just test
  just lint
  just build
  just publish

just publish creates a main-program-only dist/pair-recon-<version>-<os>-<cpu>.zip for the current platform. Build the full Windows artifact on Windows x64. After extraction, run run.cmd; target users do not install Python. The ZIP excludes DBX/GitLab tools, source documentation, setup SQL, and credentials. Windows publishing includes pyodbc for Hadoop; non-Windows portable builds currently omit Hadoop/pyodbc. Databricks authentication, Oracle credentials, Outlook, and ODBC drivers remain external.

Live tests are opt-in. Do not run just live unless real source credentials and network access are intended.
