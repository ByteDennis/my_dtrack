 DTRACK — WEB STACK SELF-STUDY GUIDE
================================================================================

Audience: Junior web dev who needs to maintain & extend the dtrack web UI.
Goal:     After reading this you can troubleshoot any HTML / CSS / JS file in
          this repo, read the FastAPI backend, and add a new feature end-to-end.
Updated:  2026-05-19

How to use this file: read top to bottom once. Then keep it open while
clicking through the actual codebase — every section points at real
files in `dtrack/web/` so you can match concepts to code.


================================================================================
 0.  MENTAL MODEL — WHAT HAPPENS WHEN YOU CLICK A BUTTON
================================================================================

Every page in dtrack lives in this 4-layer loop. Memorize it; everything
else is detail.

    1. BROWSER asks the server for a URL  (e.g. GET /load_row)
       │
       ▼
    2. FASTAPI route handler in web/app.py:159 returns rendered HTML
       (built from a Jinja2 template in web/templates/*.html)
       │
       ▼
    3. BROWSER parses HTML, loads /static/style_v2.css and /static/*.js,
       fires DOMContentLoaded → page-specific JS runs initialization
       (e.g. load_row.js:8 calls loadKnownTables() + refreshDbStatus())
       │
       ▼
    4. User clicks something. JS handler runs. If it needs data:
          fetch('/api/...') → FASTAPI /api/... route → SQLite / extractor
          → JSON response → JS updates the DOM → user sees new content
       (no page reload involved — this is the "single page" feel)

The web UI is just glue. All real work happens in Python (db.py,
compare.py, platforms/). JS's job is to ferry user input → /api/* and
ferry results back into the DOM. If you internalize that, 80% of
debugging is "where in the loop did it break?"


================================================================================
 1.  HTML — JUST ENOUGH
================================================================================

HTML is a tree of nested tags. dtrack uses ~15 tag kinds total; you don't
need to know the other 100.

Common tags you'll see in templates/*.html:

    <div>      box container, no semantic meaning
    <section>  same as <div> but signals "logical section"
    <header>   page banner (top bar)
    <main>     primary content area
    <h1>..<h6> headings (used for hierarchy + default styling)
    <p>        paragraph
    <span>     inline box (for styling a piece of text without a line break)
    <a>        link
    <button>   button
    <input>    form input (text, file, checkbox, radio, …)
    <select> + <option>   dropdown
    <table> + <thead>/<tbody>/<tr>/<td>   table
    <ul>/<ol> + <li>      list
    <script>   inline or external JS
    <link>     external CSS

Each tag can carry **attributes** like:

    <button id="refresh-db-btn" class="btn-text" onclick="refreshDB()"
            title="Refresh DB">Refresh DB</button>

Attributes that matter for you:
    id="..."       unique identifier on the page (look up with getElementById)
    class="..."    one or more CSS class names (look up with querySelector)
    onclick="..."  inline event handler — calls a JS function on click
    data-foo="..." custom data attached to an element (read with el.dataset.foo)
    style="..."    inline CSS (e.g. style="display:none" to hide)

Real example — open templates/load_row.html and notice:
    <input type="file" id="file-input" multiple accept=".csv" style="display:none">
    <button class="btn-secondary" id="browse-btn">Browse Files</button>

`#file-input` is hidden visually but the JS clicks it programmatically:

    document.getElementById('browse-btn').onclick = () => {
        document.getElementById('file-input').click();
    };

A common idiom — show a native file picker without using the ugly default
<input type="file"> styling.


================================================================================
 2.  JINJA2 TEMPLATES — HTML WITH PLACEHOLDERS
================================================================================

dtrack uses Jinja2 (FastAPI's `Jinja2Templates`). It looks like HTML but
has `{{ ... }}` for variables and `{% ... %}` for control flow.

Look at templates/_layout.html — the base template every page extends:

    <title>dtrack{% if page_title %} - {{ page_title }}{% endif %}</title>
    ...
    {% for k, label in steps %}
    <option value="{{ k }}"{% if current_page == k %} selected{% endif %}>
        {{ label }}
    </option>
    {% endfor %}

Three Jinja constructs you'll meet:

    {{ var }}              insert a Python variable's value
    {% if x %}...{% endif %}   conditional
    {% for x in xs %}...{% endfor %}   loop

And **template inheritance** — every page file starts like this:

    {% extends "_layout.html" %}
    {% set current_page = "load_row" %}
    {% set page_title = "Load Row Data" %}

    {% block content %}
        <!-- page-specific HTML goes here -->
    {% endblock %}

This says: take _layout.html (which has header + footer + script tags),
and fill in the `content` slot with whatever's between `{% block content %}`
and `{% endblock %}`. Same trick for `{% block scripts %}`.

Templates render on the SERVER (Python). The variables come from
FastAPI route handlers calling `templates.TemplateResponse(...)`. By the
time the browser sees the HTML, Jinja is gone — the browser only ever
sees plain HTML. View Page Source (Ctrl+U) shows you exactly what
Jinja produced.

Troubleshooting Jinja: if `{{ foo }}` shows up literally in the browser,
the variable wasn't passed in. If you see no output at all where you
expected content, check whether `{% block content %}` is spelled right
in BOTH the parent and child templates.


================================================================================
 3.  CSS — JUST ENOUGH
================================================================================

CSS rules look like this:

    .card {                       /* selector */
        padding: 16px;            /* declarations */
        border-radius: 8px;
        background: var(--card-bg);
    }

Selectors you'll see in dtrack:

    .card           any element with class="card"
    #drop-zone      element with id="drop-zone"
    button          every <button> tag
    .card h2        every <h2> INSIDE a .card
    .rc-row.excl    element with BOTH class="rc-row" AND class="excl"
    button:hover    button when mouse is over it
    [data-state="ok"]   element with attribute data-state="ok"

dtrack's CSS lives in `web/static/style_v2.css`. Naming convention:

    .rc-*       row compare components
    .cm-*       column mapping components
    .btn-*      button variants
    .card       generic card container
    .data-table standard data table

CSS variables (`var(--name)`) are used for theming. They're defined at
the top of style_v2.css inside `:root { ... }`. Change one variable, the
whole UI re-themes. Dark mode is just a different :root rule.

Inline overrides:
    <div style="display:none">...</div>      hide an element via inline style

This is what JS does when toggling visibility — `el.style.display = 'none'`
or `el.style.display = 'block'`.

DEBUG CSS: DevTools → Elements tab → click an element → right side
"Styles" panel lists every rule applied, in cascade order. Crossed-out
rules lost to a more specific rule. Edit values inline to test fixes
before changing the file.


================================================================================
 4.  JAVASCRIPT — THE LANGUAGE PARTS YOU NEED
================================================================================

dtrack JS files are plain ES2017+ (no TypeScript, no React, no build
step). What you need to know, in increasing depth:

4.1  VARIABLES
     const x = 1;        // can't be reassigned (use this by default)
     let   y = 2;        // can be reassigned (use when you need to)
     // never use `var` in new code

4.2  STRINGS — template literals (backticks)
     const name = 'world';
     const msg = `hello, ${name}!`;       // backticks, ${expr}
     const html = `<div class="x">${pair.name}</div>`;
     // \n is allowed inside backticks → multi-line strings without "+"

4.3  ARRAYS — methods that return new arrays (don't mutate)
     const xs = [1, 2, 3];
     xs.map(x => x * 2)        // [2, 4, 6]
     xs.filter(x => x > 1)     // [2, 3]
     xs.find(x => x === 2)     // 2   (or undefined)
     xs.forEach(x => console.log(x))   // side effects only
     xs.length                 // 3

     Real example from load_row.js:13-23:
         const tables = (data.pairs || [])
             .filter(p => !p.skip)
             .map(p => ({
                 pair_name: p.pair_name,
                 table_left: p.table_left,
                 ...
             }));
     Reads as: "take data.pairs (or empty array if missing), keep the
     ones that aren't skipped, transform each into a smaller shape."

4.4  OBJECTS — like Python dicts
     const p = { name: 'loans', source: 'oracle', cols: 12 };
     p.name                    // 'loans'    (dot access)
     p['name']                 // 'loans'    (bracket access — for dynamic keys)
     p.name = 'new'            // mutate
     const { name, source } = p   // destructuring: pulls 2 keys into locals
     const p2 = { ...p, name: 'x' }   // spread: shallow copy with override

4.5  OPTIONAL CHAINING + NULLISH COALESCING (very common in dtrack)
     p?.left?.source           // safe — undefined if p or p.left is null
     data.loaded ?? 0          // 0 if data.loaded is null OR undefined
                               // (different from || which also catches 0, '', etc.)

4.6  FUNCTIONS — three forms, all equivalent for our purposes
     function f(x) { return x + 1; }     // declaration
     const f = function(x) { return x + 1; }   // expression
     const f = x => x + 1;               // arrow — preferred for short callbacks
     const f = (x, y) => { ... return z; }     // arrow with body

     Arrow functions differ from regular ones in one important way:
     `this` is inherited from the enclosing scope. In dtrack we almost
     never use `this`, so just always use arrows for callbacks.

4.7  TRY / CATCH — error handling
     try {
         const data = JSON.parse(input);
         use(data);
     } catch (e) {
         alert('Bad JSON: ' + e.message);
     }
     // `e` is the Error object; e.message is the human-readable string.

4.8  TRUTHINESS — important for "if (x)"
     Falsy: false, 0, '', null, undefined, NaN
     Everything else is truthy — including empty arrays [] and empty
     objects {}. This bites people. To check "is this array empty",
     write `if (xs.length === 0)`, NOT `if (!xs)`.

4.9  EQUALITY — always use === not ==
     '1' == 1     // true  (== does type coercion — avoid)
     '1' === 1    // false (=== is strict — use this)
     null == undefined   // true  (one exception some people allow)


================================================================================
 5.  THE DOM — HOW JS TOUCHES HTML
================================================================================

The browser parses your HTML into a tree of "nodes" — the DOM. JS gets
a reference to this tree via the global `document` object.

5.1  FINDING ELEMENTS
     document.getElementById('drop-zone')           // by id
     document.querySelector('.card.active')         // by CSS selector, first match
     document.querySelectorAll('.rc-row')           // all matches (NodeList — array-like)
     parent.querySelector('button')                 // scoped within parent

5.2  READING / WRITING CONTENT
     el.textContent = 'hello'              // plain text (safe — no HTML parsing)
     el.innerHTML  = '<b>hi</b>'           // HTML (parsed — DANGEROUS for user input)
     el.value                              // for <input>, <select>, <textarea>
     el.checked                            // for <input type="checkbox">
     el.dataset.foo                        // reads data-foo="..." attribute

     RULE: use textContent unless you're inserting HTML you constructed
     yourself. If you EVER do `el.innerHTML = userInput`, you have an
     XSS bug. dtrack works around this by always building HTML
     programmatically with template literals from trusted data.

5.3  STYLING + VISIBILITY
     el.style.display = 'none'              // hide
     el.style.display = 'block'             // show (block-level)
     el.style.display = ''                  // revert to stylesheet default
     el.classList.add('active')
     el.classList.remove('active')
     el.classList.toggle('active')
     el.classList.contains('active')        // boolean

5.4  CREATING + INSERTING
     const div = document.createElement('div');
     div.className = 'card';
     div.textContent = 'hi';
     parent.appendChild(div);              // add as last child
     parent.insertBefore(div, parent.firstChild);   // add as first child
     div.remove();                         // remove from DOM

5.5  EVENTS — wiring up handlers
     btn.addEventListener('click', (e) => { ... });
     // OR (older style, used in dtrack templates):
     <button onclick="myFunc()">  + function myFunc() in JS
     // The onclick="..." form requires `myFunc` to be a GLOBAL function.

     Useful event kinds: 'click', 'change', 'input', 'submit', 'keydown',
     'dragenter'/'dragover'/'drop', 'DOMContentLoaded'.

     Always wait for DOMContentLoaded before touching the DOM at load:
         document.addEventListener('DOMContentLoaded', () => {
             initLoader();
             // ...
         });
     (See load_row.js:8 for the real version.)

5.6  COMMON PITFALL
     getElementById returns `null` if the id isn't found. Reading from
     null crashes:
         document.getElementById('typo').value   // TypeError

     Defensive pattern dtrack uses:
         const el = document.getElementById('db-summary');
         if (!el) return;
         el.innerHTML = '...';


================================================================================
 6.  ASYNC PROGRAMMING — THE BIG ONE
================================================================================

This is the part of JS that trips people up most. Read this section
twice. Then look at the real `uploadColCsv` walkthrough in section 9 and
it'll click.

6.1  WHY ASYNC EXISTS
     JavaScript is single-threaded. There's ONE thread running your code
     in the browser tab. If a network request to /api/extract takes 5
     seconds, you cannot afford to "wait" — the browser would freeze
     (no clicks, no scrolling, no rendering) for those 5 seconds.

     Solution: instead of blocking, the slow operation returns
     immediately with a PROMISE — a placeholder for the eventual result.
     Your code attaches a callback ("when the result arrives, run this").
     The thread is then free to handle other events. When the network
     reply comes back, the browser queues your callback and runs it on
     the next free moment.

6.2  THE THREE SHAPES OF ASYNC CODE — same thing, different syntax

     A) Callbacks (old, you'll rarely write but might encounter):
         setTimeout(() => console.log('hi'), 1000);
         // 1 second later, the arrow function runs

     B) Promises with .then() (mid-2010s era):
         fetch('/api/status')
             .then(resp => resp.json())     // resp.json() also returns a promise!
             .then(data => render(data))
             .catch(err => console.error(err));

     C) async/await (modern, preferred):
         async function loadStatus() {
             try {
                 const resp = await fetch('/api/status');
                 const data = await resp.json();
                 render(data);
             } catch (err) {
                 console.error(err);
             }
         }

     B and C do the EXACT same thing. async/await is just syntactic
     sugar over .then(). Most of dtrack uses C. Use C in new code.

6.3  KEY RULES OF async/await

     RULE 1: Only inside an `async` function can you use `await`.
             async function foo() {
                 const x = await fetch('/a');   // OK
             }
             function bar() {
                 const x = await fetch('/a');   // SYNTAX ERROR
             }

     RULE 2: An `async` function ALWAYS returns a Promise — even if you
             return a plain value:
                 async function f() { return 1; }
                 f();                  // → Promise<1>, NOT 1
                 const x = await f();  // → 1
                 f().then(x => ...);   // also works

     RULE 3: `await expr` does two things:
             a) waits for `expr` (if it's a Promise) to resolve
             b) hands the resolved value back as the expression result
             During the wait, the JS engine is free to do other work.

     RULE 4: Errors propagate through await like sync errors:
             async function f() {
                 const resp = await fetch('/api/x');     // rejects → throws here
                 const data = await resp.json();         // parse error → throws here
                 if (!resp.ok) throw new Error(data.error);  // manual throw
                 return data;
             }
             Wrap in try/catch when you want to handle them.

     RULE 5: `await` only waits for what you tell it. If you forget the
             `await`, you get the Promise back instead of the value, and
             your code keeps going BEFORE the network is done:
                 const data = fetch('/api/x');      // BUG — data is a Promise
                 console.log(data.status);          // undefined
             Fix:
                 const resp = await fetch('/api/x');
                 console.log(resp.status);          // 200

6.4  RUNNING THINGS IN PARALLEL — Promise.all

     Sequential (slow — 2 round trips back to back):
         const a = await fetch('/api/x');
         const b = await fetch('/api/y');

     Parallel (fast — both go out at the same time):
         const [a, b] = await Promise.all([
             fetch('/api/x'),
             fetch('/api/y'),
         ]);

     Use Promise.all when the requests are independent. If b depends on
     a's result, stay sequential.

6.5  THE EVENT LOOP — a 30-second model
     Browser has a queue of "things to run". Each turn it takes one
     item off the queue, runs it to completion (no preemption), then
     loops. When you `await`, your function pauses and the browser
     starts processing other queue items (user clicks, timer fires,
     network completions). When the awaited promise resolves, your
     function resumes from where it paused, on a future turn of the loop.

     Consequence: between `await` and the next line, ANYTHING can
     happen. The user might click a button that mutates the state your
     function was about to read. This is why async bugs are sneaky —
     they look sequential but they're not atomic.

6.6  COMMON ASYNC MISTAKES

     M1: Forgetting `async` on the wrapper function
         document.addEventListener('click', () => {
             await fetch(...)        // SYNTAX ERROR
         });
         // Fix:
         document.addEventListener('click', async () => {
             await fetch(...)
         });

     M2: Awaiting inside a non-async map callback
         xs.map(x => await foo(x))   // SYNTAX ERROR
         // Fix:
         await Promise.all(xs.map(x => foo(x)))   // parallel
         // OR
         for (const x of xs) { await foo(x); }    // sequential

     M3: Treating fetch like the result
         fetch('/api/x').data           // undefined — fetch is a Promise
         // Fix:
         const resp = await fetch('/api/x');
         const data = await resp.json();

     M4: Not handling errors → silent failures
         async function f() {
             await fetch('/api/x');      // if this 500s, nothing tells the user
         }
         // Fix: try/catch + show feedback (alert, apiLog, status badge)


================================================================================
 7.  fetch + JSON + FormData — THE DTRACK NETWORK PATTERN
================================================================================

Every JS file in dtrack talks to FastAPI via `fetch`. There are exactly
three patterns to learn:

7.1  GET — no body, JSON response
     const resp = await fetch('/api/status');
     if (!resp.ok) throw new Error(`HTTP ${resp.status}`);
     const data = await resp.json();

     With query parameters:
         const params = new URLSearchParams({ from_date: '2026-01-01' });
         const resp = await fetch(`/api/foo?${params}`);

7.2  POST with JSON body
     const resp = await fetch('/api/extract', {
         method: 'POST',
         headers: { 'Content-Type': 'application/json' },
         body: JSON.stringify({ platform: 'aws', type: 'row' }),
     });
     const data = await resp.json();

7.3  POST with multipart/form-data (file upload)
     const form = new FormData();
     form.append('file', fileObject);            // a File from <input type="file">
     form.append('table_name', 'aws_loans');
     const resp = await fetch('/api/load/columns/upload', {
         method: 'POST',
         body: form,                              // NO Content-Type header — browser sets it
     });
     const data = await resp.json();

     Important: do NOT set Content-Type when using FormData. The browser
     automatically sets it with the correct multipart boundary. Setting
     it manually breaks the upload.

7.4  THE FETCH INTERCEPTOR (common.js:306)
     dtrack wraps `window.fetch` so every /api/* call is auto-logged to
     the API Log panel at the bottom right of every page:

         GET status → 200 (12ms)
         POST load/columns/upload → 200 (340ms) ok loaded=42
         PUT compare/row/loans → 500 (8ms)
           req: {"matching_dates":[...]}
           error: NoneType has no attribute 'split'

     This means: you don't need DevTools to see what the network is
     doing. The panel shows it all, including request bodies on errors.
     Open the API Log first; only escalate to DevTools Network tab if
     the API Log doesn't have enough detail.


================================================================================
 8.  FASTAPI SIDE — WHAT YOU NEED TO READ
================================================================================

You don't need to write much FastAPI day-to-day; you need to READ it to
debug the other end of a /api/* call. Here's the survival kit.

8.1  ROUTE DECORATORS
     @app.get("/api/status")
     async def api_status():
         return { "pairs": [...] }
     # Decorator binds URL path + HTTP method to the handler.
     # `async def` is FastAPI's default; it doesn't mean the handler is
     # parallel — it means the handler can `await` things (DB I/O, etc.).

     @app.get   GET (read)
     @app.post  POST (create / action)
     @app.put   PUT (update)
     @app.delete  DELETE (remove)

8.2  PATH PARAMETERS
     @app.get("/api/pairs/{pair_name}")
     async def get_pair(pair_name: str):
         ...
     # JS: fetch(`/api/pairs/${encodeURIComponent(name)}`)

8.3  QUERY PARAMETERS — just function args with defaults
     @app.get("/api/compare/row/{pair_name}")
     async def compare_row(pair_name: str,
                            from_date: Optional[str] = None,
                            to_date: Optional[str] = None):
         ...
     # JS: fetch('/api/compare/row/loans?from_date=2026-01-01')

8.4  JSON BODY (the most common POST shape)
     @app.post("/api/extract")
     async def api_extract(request: Request):
         body = await request.json()
         platform = body.get("platform", "aws")
         ...

     Or with a Pydantic model — typed and validated:
         from pydantic import BaseModel
         class ExtractReq(BaseModel):
             platform: str
             type: str = "row"
         @app.post("/api/extract")
         async def api_extract(req: ExtractReq):
             # req.platform, req.type
             ...

     dtrack mostly uses the Request.json() form for flexibility.

8.5  MULTIPART FORM (file upload) — see app.py:1840
     from fastapi import UploadFile, File, Form
     @app.post("/api/load/columns/upload")
     async def upload(
         file: UploadFile = File(...),     # required file
         table_name: str = Form(""),        # text field, default ""
         source: str = Form(""),
     ):
         content = await file.read()        # bytes
         text = content.decode("utf-8")
         ...
         return { "ok": True, "loaded": count }

     The JS pairs with this exactly:
         const form = new FormData();
         form.append('file', file);
         form.append('table_name', 'aws_loans');
         form.append('source', 'aws');
         await fetch('/api/load/columns/upload', { method:'POST', body: form });

8.6  RESPONSES
     Plain dict           → automatic JSON, status 200
     JSONResponse(...)    → JSON with custom status/headers
     HTMLResponse(...)    → HTML body
     RedirectResponse(...) → 3xx redirect
     FileResponse(...)    → stream a file from disk
     StreamingResponse(...) → SSE / chunked output (dtrack uses this for live SQL execution)

     Returning an error:
         return JSONResponse(status_code=400, content={"error": "table_name is required"})
     The JS side sees `resp.ok === false` and `resp.status === 400`.

8.7  THE REQUEST LIFECYCLE
     1) Browser fetch hits uvicorn (ASGI server inside FastAPI)
     2) The middleware in web/app.py:31 (`_APILogMiddleware`) intercepts,
        logs method/path/body to stdout, replays the body to the handler
     3) FastAPI matches the route, parses path/query/body
     4) Your handler runs. If it `await`s, the worker thread is free
        for other requests during the wait.
     5) Return value → JSON-encoded → sent back
     6) JS `await fetch(...)` resolves with the Response object

8.8  WHERE STATE LIVES
     FastAPI itself is stateless across requests. dtrack stores state in:
       - SQLite (via dtrack/db.py) — durable
       - pairs.json — durable, user-edited
       - module-level globals like _db_path, _config_path — process lifetime only
     Two different `dtrack serve` processes do NOT share state. The
     web UI is a single-process design.


================================================================================
 9.  WORKED EXAMPLE — uploadColCsv (web/static/load_row.js:135)
================================================================================

We'll build this function from scratch. By the end you'll understand
every line of dtrack JS.

GOAL: When the user clicks "upload" next to a table in the DB summary,
let them pick a CSV file from their disk, send it to the server with
the table name attached, and refresh the page's status panel afterwards.

THE FINAL CODE:

    function uploadColCsv(tableName, source) {
        const input = document.createElement('input');
        input.type = 'file';
        input.accept = '.csv';
        input.onchange = async () => {
            const file = input.files[0];
            if (!file) return;
            const form = new FormData();
            form.append('file', file);
            form.append('table_name', tableName);
            form.append('source', source);
            try {
                const resp = await fetch('/api/load/columns/upload', {
                    method: 'POST', body: form
                });
                const data = await resp.json();
                if (!resp.ok) throw new Error(data.error || 'Upload failed');
                await refreshDbStatus();
            } catch (e) {
                alert('Column upload failed: ' + e.message);
            }
        };
        input.click();
    }

NOW LINE BY LINE.

STEP 0 — Where does this even get called from?
    Open templates' rendered HTML in DevTools. The "upload" button is
    generated in load_row.js:96:
        `<button class="btn-text" onclick="uploadColCsv('${p.table_left}', '${p.source_left}')">upload</button>`
    The onclick attribute names our function and passes two args. So
    uploadColCsv MUST be a global function (declared at file scope, not
    inside another function). That's why we wrote `function uploadColCsv(...)`,
    not `const uploadColCsv = ...` inside an IIFE.

STEP 1 — Create a file input element that's NOT in the page yet
    const input = document.createElement('input');
    input.type = 'file';
    input.accept = '.csv';

    Why not put <input type="file"> in the template? Two reasons:
      1) We need a fresh one each click; the user might re-upload a
         different file to a different table.
      2) Browsers won't open a file picker except in response to a real
         user gesture (security). By creating the input and clicking it
         inside the onclick handler, the gesture chain is preserved.

    At this point `input` exists in memory but isn't visible. It's a
    DOM node that's not attached to the page. That's fine — we never
    intend the user to see it; we just want its file picker dialog.

STEP 2 — Wire up "when the user picks a file" BEFORE clicking
    input.onchange = async () => {
        ...
    };

    `onchange` fires after the user picks a file. We attach an `async`
    arrow function because the work inside involves `await`. Note we're
    not calling the function — we're storing it. It runs later, when
    the user picks a file (or never, if they cancel the dialog).

    THIS IS THE CRUX OF EVENT-DRIVEN PROGRAMMING. You don't run code
    "now"; you describe what to do "when X happens" and hand it off.

STEP 3 — Trigger the dialog
    input.click();

    This synthesizes a click on the hidden input. The browser opens
    the OS file picker. uploadColCsv returns immediately AT THIS POINT.
    The function is "done" — but the onchange handler is now armed and
    waiting.

    Important: if you put any code AFTER input.click(), it would run
    BEFORE the user picks a file. That's why the whole upload logic is
    inside onchange.

STEP 4 — User picks a file, onchange fires
    const file = input.files[0];
    if (!file) return;

    `input.files` is a FileList (array-like). [0] is the chosen file.
    If the user cancelled, `files` is empty and `file` is undefined —
    bail out silently. (Cancellation doesn't actually fire onchange in
    most browsers, but defensive coding never hurts.)

STEP 5 — Pack the upload payload
    const form = new FormData();
    form.append('file', file);
    form.append('table_name', tableName);
    form.append('source', source);

    FormData is the API for building a multipart/form-data body. It's
    what the browser builds for you when you submit a <form> the old-
    fashioned way; here we build it manually.

    Field names ('file', 'table_name', 'source') MUST match what the
    FastAPI handler expects. Look at app.py:1840 — the handler
    declares:
        async def api_load_columns_upload(
            file: UploadFile = File(...),
            table_name: str = Form(""),
            source: str = Form(""),
        ):
    If we'd written form.append('tableName', ...), the backend would
    see table_name="" (its default) — silent bug.

STEP 6 — Send it
    const resp = await fetch('/api/load/columns/upload', {
        method: 'POST',
        body: form,
    });

    `await` pauses the handler until the response is back. While paused,
    the browser is still responsive — other clicks, scrolls, etc. work.
    No Content-Type header — see section 7.3.

STEP 7 — Parse the response
    const data = await resp.json();
    if (!resp.ok) throw new Error(data.error || 'Upload failed');

    `resp.json()` itself returns a Promise — parsing the body is async
    because it has to wait for the rest of the body bytes to arrive.

    `resp.ok` is true for HTTP 200-299, false otherwise. We check it
    AFTER reading the body so we can include the server's error
    message in our thrown Error. Throwing here jumps to the catch
    block — the next `await` never runs.

STEP 8 — Refresh dependent UI
    await refreshDbStatus();

    The upload changed _column_meta in the DB. The DB-summary panel
    is showing stale data. refreshDbStatus() re-fetches /api/status
    and re-renders the panel. The `await` makes sure the panel is
    actually updated before our function returns — useful if the
    caller chains anything after.

STEP 9 — Error handling
    } catch (e) {
        alert('Column upload failed: ' + e.message);
    }

    Anything thrown in the try block (network error, !resp.ok, JSON
    parse error, anything in refreshDbStatus) lands here. We show a
    simple alert. In real production you'd use a non-blocking toast,
    but alert() is fine for an internal tool.

THE TIMELINE — what happens when the user clicks "upload":

    t=0     uploadColCsv called → creates <input>, attaches onchange,
            calls input.click() → returns
    t=0+    OS file picker pops up
    t=...   User picks a file
    t=N     onchange fires → builds FormData → fetch starts
    t=N+    fetch in flight, page still responsive
    t=N+M   server responds → resp.json() awaited → success or error
    t=N+M+  refreshDbStatus runs → /api/status fetched → DB summary re-rendered

    The original `uploadColCsv` invocation ended at t=0+, but the work
    it kicked off continues for as long as needed.

10.  DEBUGGING WORKFLOW
================================================================================

10.1  ALWAYS START WITH THE API LOG PANEL
      Every page has it at the bottom-right (the "API Log" tab). Click
      it. Every /api/* call is there, with timing, status, and (on
      errors) the request body + server error message.

      If the API Log shows the call worked but the UI didn't update →
      bug is in the JS render code (use `debugger;`).
      If the API Log shows an error → bug is in the backend (look up
      the route in app.py and add print()/ipdb).
      If the API Log shows nothing → the JS never made the call (your
      event handler isn't wired up, or there's a syntax error earlier
      in the same file).

10.2  USING `debugger;`
      Drop the literal word `debugger;` as a statement inside any JS
      file. When the browser hits it AND DevTools is open, execution
      pauses there.

      Workflow:
        1. Edit the JS file: add `debugger;` where you suspect trouble.
        2. Open DevTools (F12 or Cmd+Option+I on Mac).
        3. Hard-reload the page (Cmd+Shift+R / Ctrl+Shift+R) so the
           browser fetches the new JS, not the cached old one.
        4. Trigger the action (click the button, drop the file, etc.).
        5. Execution pauses on the `debugger;` line. DevTools auto-
           switches to the Sources tab and highlights the line.
        6. Inspect:
            - Hover over variables in source → tooltip shows current value
            - Right side "Scope" panel lists all locals, closure vars, globals
            - Console tab: type any expression to evaluate it in the
              paused scope (e.g. type `data` to see the response)
        7. Step:
            F10 = step over (run this line, stop at next)
            F11 = step into (descend into the function called on this line)
            F8  = continue (run until next debugger; or breakpoint)
        8. Resume with F8. Remove `debugger;` when done.

10.3  HOW TO CONFIRM DEVTOOLS IS OPEN
      Three quick checks:
        a) Visual: F12 toggles DevTools. If you see a panel split (the
           regular page on top/left, the DevTools UI on the
           bottom/right), it's open. If you see only the page, it's
           closed. Re-press F12 to open it.
        b) Console test: in DevTools Console tab type:
               1 + 1
           and press Enter. If you get `2` back, the Console is live
           and DevTools is definitely open.
        c) `debugger;` test: in Console type:
               debugger;
           and press Enter. If DevTools is open, the Sources tab opens
           and execution pauses. Press F8 to resume. If nothing
           happens (Console just shows `undefined`), DevTools is
           somehow not attached — close & re-open it.

      Common confusion: DevTools attaches per-tab. If you open DevTools,
      then open the dtrack page in a SECOND tab, the second tab has its
      own DevTools state (initially closed). Bring it forward and press
      F12 again.

      Another gotcha: if you docked DevTools to a different monitor
      that's currently off, it's "open" but invisible. Right-click the
      DevTools panel → "Dock to right" / "Undock into separate window"
      to bring it back.

10.4  BREAKPOINTS INSTEAD OF debugger;
      If you don't want to edit source:
        - DevTools → Sources tab
        - Left sidebar: navigate to dtrack/web/static/your_file.js
        - Click the line number gutter → blue arrow appears = breakpoint
        - Reload + trigger → pauses on that line
      Breakpoints persist across reloads (per origin + path).

      Pro tip: right-click the line number → "Add conditional breakpoint"
      → enter an expression like `pairName === 'loans'`. Pauses only
      when the condition is true. Saves you stepping past 50
      uninteresting iterations.

10.5  WHEN A FILE WON'T HOT-RELOAD
      uvicorn's default doesn't watch the static/ folder. After editing
      JS or CSS:
        - Hard reload: Ctrl+Shift+R (or Cmd+Shift+R on Mac).
        - Or: DevTools → Network tab → check "Disable cache". Then a
          plain reload always fetches fresh assets (only works while
          DevTools is open).
      After editing a .html template OR any .py file: restart `dtrack
      serve` entirely (templates are loaded by FastAPI; Python isn't
      reloaded without --reload uvicorn flag).

10.6  READING UNFAMILIAR ERRORS
      Console errors show a stack trace. Click the top filename:line
      link — DevTools jumps to that line. Read upward through the
      stack to find the deepest user code (skip framework internals).

      Common error patterns:
        "Cannot read properties of null (reading 'X')"
            → you called .X on something that's null. Usually
              getElementById('typo') or a missing API response field.
              Add a `if (!obj) return;` guard or check the API response.
        "Unexpected token < in JSON at position 0"
            → fetch got HTML (probably a 500 error page) but tried to
              parse it as JSON. Check Network tab — the server's
              response is HTML, not JSON. Look at the actual HTTP status.
        "is not a function"
            → typo'd a method name, or the value isn't what you think.
              `console.log(typeof x, x)` to see what x actually is.
        CORS errors
            → you're fetching from a different origin than the page.
              Shouldn't happen with dtrack since everything is same-origin.

11.  ADDING A NEW FEATURE — END-TO-END RECIPE
================================================================================

Scenario: add a button on /load_row that exports the DB-summary panel
as a CSV.

11.1  PLAN
      Frontend: a new <button> in load_row.html. On click, fetch a new
      endpoint, get back CSV bytes, trigger a browser download.
      Backend: new /api/load/row/export-summary endpoint that reads
      from _metadata via db.py and returns a CSV.

11.2  BACKEND — add the endpoint
      Edit web/app.py, somewhere near the other /api/load/row/* routes:

          @app.get("/api/load/row/export-summary")
          async def api_export_row_summary():
              from ..db import list_tables, get_metadata
              import csv as csv_mod, io as io_mod
              tables = list_tables(_db_path)
              buf = io_mod.StringIO()
              w = csv_mod.writer(buf)
              w.writerow(['table', 'source', 'min_date', 'max_date', 'rows'])
              for t in tables:
                  meta = get_metadata(_db_path, t['table_name']) or {}
                  w.writerow([t['table_name'], t.get('source',''),
                              meta.get('min_date',''), meta.get('max_date',''),
                              meta.get('row_count_total','')])
              return Response(content=buf.getvalue(),
                              media_type='text/csv',
                              headers={'Content-Disposition':
                                       'attachment; filename="row_summary.csv"'})

      Restart `dtrack serve` so the new route is picked up.

      Sanity check first — open the URL directly in the browser:
        http://localhost:8080/api/load/row/export-summary
      Should download a CSV. If it doesn't, fix the backend before
      touching the frontend.

11.3  FRONTEND — add the button + handler
      In templates/load_row.html, inside the DB STATUS card's
      .section-header div:

          <button class="btn-secondary" id="export-summary-btn"
                  onclick="exportRowSummary()">Export CSV</button>

      In static/load_row.js, add at file scope:

          async function exportRowSummary() {
              try {
                  const resp = await fetch('/api/load/row/export-summary');
                  if (!resp.ok) throw new Error(`HTTP ${resp.status}`);
                  const blob = await resp.blob();
                  const url = URL.createObjectURL(blob);
                  const a = document.createElement('a');
                  a.href = url;
                  a.download = 'row_summary.csv';
                  document.body.appendChild(a);
                  a.click();
                  a.remove();
                  URL.revokeObjectURL(url);
              } catch (e) {
                  alert('Export failed: ' + e.message);
              }
          }

      Reload the page. Click the button → file should download. If not:
        - API Log shows the request → backend issue → curl the URL
        - API Log shows nothing → button wiring issue → check id /
          onclick / spelling

11.4  PATTERN BEHIND THE RECIPE
      Every feature in dtrack follows the same template:
        a) Decide the contract (URL, method, request body, response shape).
        b) Implement + manually test the backend first (curl or browser).
        c) Wire up the frontend (button, handler, fetch, DOM update).
        d) Debug front-back asymmetries via the API Log panel.

      Front-back disagreements are the #1 source of bugs:
        - Frontend sends `tableName`, backend reads `table_name`
        - Frontend POSTs as JSON, backend declared multipart
        - Backend returns `{error: "..."}` with 200, frontend checks
          `resp.ok` (passes) but then can't find a useful field
      Use the API Log + DevTools Network tab to inspect the actual wire
      content. ALWAYS verify the contract end-to-end before assuming
      "it should work."

12.  DTRACK-SPECIFIC IDIOMS — SHORTCUTS YOU'LL SEE OFTEN
================================================================================

12.1  GLOBAL HELPERS in common.js
      refreshDB()          POST /api/init — recreate / refresh DB
      apiLog(msg, type)    push a line to the bottom-right log panel
                            (type: 'info' | 'success' | 'error')
      openGlobalPairPicker()   modal to filter pairs across all pages
      The fetch interceptor (wraps window.fetch) — already on, no setup.

12.2  PAGE INIT PATTERN
      Almost every page JS starts the same way:
          document.addEventListener('DOMContentLoaded', async () => {
              initSomething();
              await loadKnownTables();
              await refreshDbStatus();
          });
      DOMContentLoaded fires when the HTML is parsed but before images
      load. It's safe to query the DOM at this point.

12.3  TEMPLATE-LITERAL HTML BUILDERS
      Instead of createElement + appendChild towers, dtrack builds
      strings and assigns to .innerHTML. Example from load_row.js:

          const rows = pairs.map(p => {
              const lr = p.left.row_count || 0;
              return `
                  <tr>
                      <td>${p.pair_name}</td>
                      <td>${lr.toLocaleString()}</td>
                      ...
                  </tr>
              `;
          }).join('');
          el.innerHTML = `<table>${rows}</table>`;

      Safe because all the inputs are server-controlled (pair names,
      counts). NEVER do this with user-typed input.

12.4  DEBOUNCING — fire ONLY after the user stops typing
      Pattern seen in row_compare.js:
          let _syncTimer = null;
          function debouncedSync(name) {
              clearTimeout(_syncTimer);
              _syncTimer = setTimeout(() => syncPair(name), 600);
          }
      Every event resets the timer. The real call happens 600ms after
      the LAST event. Used so 20 rapid checkbox toggles only result in
      one save.

12.5  ?-OPTIONAL CHAINING + ?? FALLBACK
      Already covered in 4.5 but you'll see this everywhere:
          const tables = (data.pairs || []).filter(p => !p.skip);
          const src = p.left?.source || '';
          const count = data.loaded ?? 0;

12.6  SHARED LOADER — csv_loader.js
      load_row.js and load_col.js both call createCsvLoader({...}). It's
      a factory that returns { init() } with the drop-zone, scan, match,
      upload logic. The two pages differ only in config (suffix,
      endpoint, formatLoadResult). Read csv_loader.js once — it's the
      single most reused chunk of frontend code in dtrack.

13.  QUICK REFERENCE — "I WANT TO …"
================================================================================

  "find what backend endpoint a button hits"
      → DevTools Network tab + click the button. Right-click the
        request → Copy as cURL for repro. Or search the JS file for
        the function name in the onclick attribute.

  "find what JS function a button calls"
      → DevTools Elements tab, click the button → inspect the
        onclick="..." attribute. Or grep `web/static/` for the button id.

  "see what data the backend returned"
      → Network tab → click the request → Response tab. Or expand
        the API Log entry. Or add `console.log(data)` after `resp.json()`
        and reload.

  "make a request from JS, see exactly what was sent"
      → DevTools Network tab → request → Payload / Headers tabs.

  "inject a value into the page from Python"
      → Pass it in `templates.TemplateResponse(..., context={"x": 1})`
        then use `{{ x }}` in the template, or stash it on a hidden
        <input> the JS reads, or render it as JSON into a <script>:
            <script>window.__INITIAL_DATA__ = {{ data | tojson }};</script>

  "share JS state across pages"
      → localStorage / sessionStorage. Or pass it through URL params.
        Or persist to the DB and re-fetch on page load (dtrack's
        usual approach).

  "test the backend without the frontend"
      → curl 'http://localhost:8080/api/status' | jq .
      → curl -X POST -H 'Content-Type: application/json' \
             -d '{"platform":"aws","type":"row"}' \
             http://localhost:8080/api/extract

  "test the frontend without a live backend"
      → DevTools Sources tab → Override response. Or temporarily
        replace `fetch` with a stub that returns canned data. Or use
        the DTRACK_MOCK env var when launching the backend so /api/*
        runs against fixture CSVs.

  "find every place that calls /api/foo"
      → grep -rn '/api/foo' dtrack/web/static/

  "find every page that uses a helper function"
      → grep -rn 'helperName' dtrack/web/static/ dtrack/web/templates/

If you have a week and want to level up:

  Day 1:  Read this file once. Open every section's referenced source
          line. Don't try to memorize — just match concepts to code.

          Trace one click action through JS → fetch → app.py route →
          db.py call → response → DOM update. Use the API Log.

          rewrite them as .then() chains. Watch how ugly it gets.
          You'll appreciate async/await viscerally.
  Day 4:  Add a small feature using section 11's recipe. e.g. add a
          "Last refreshed" timestamp to one of the panels.
  Day 5:  Break something on purpose. Delete a closing }. Forget an
          await. Misspell an endpoint. Watch how each failure manifests.
          Learn to recognize them.
  Day 6:  Read pairs.js — the biggest, most complex JS file. By now
          most patterns should look familiar.
  Day 7:  Sit down at the codebase cold and add a real feature start to
          finish. If you can do this without re-reading the tutorial,
          you're done.
