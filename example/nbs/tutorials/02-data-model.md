# 02 — Data model (SQLite schema + JSON config)

Everything dtrack persists lives in **one SQLite database** (default
`project.db`) defined by the dict `_SCHEMA` at the top of `dtrack/db.py`.
The JSON config file (`dtrack.json`) describes **what the user wants to
compare**; the SQLite db holds **what dtrack has discovered and computed**.
This tutorial covers both, and shows how each table is populated and read.

## 1. SQLite schema (`_SCHEMA`)

The truth is `dtrack/db.py:15–134`. Eight tables, every CREATE TABLE statement
is generated by `_build_create_sql(table_name)` from this dict so any drift
between `init_database` and `refresh_database` is mechanical, not philosophical.

### 1.1 `_metadata` — one row per loaded table

| Column            | Notes                                                        |
| ----------------- | ------------------------------------------------------------ |
| `table_name`      | PRIMARY KEY — the qname (`source.schema.table`). Tutorial 06 explains how qnames are built. |
| `source`          | "aws" / "oracle" / "hadoop" / "databricks" / "csv" / "sas".  |
| `source_table`    | Raw table name as it appears at the source.                  |
| `date_var`        | The user-declared date column for per-date splits.           |
| `row_count_total` | Sum of `_row_counts.row_count` for this table.               |
| `vintage`         | "all", "year", "quarter", "month", "week", "day", or "sample". |
| `data_type`       | The `date_type` declared in config (date / datetime / number / yyyy-mm-dd / …). |
| `date_format`     | Free-text format string when `data_type` doesn't pin it.     |
| `min_date_loaded` / `max_date_loaded` | Span observed in `_row_counts` after load. |

Refreshed by `refresh_metadata_from_data(db_path)` — handy after a manual
SQLite edit.

### 1.2 `_col_stats` — one row per (table, column, vintage-bucket)

| Column        | Notes                                                            |
| ------------- | ---------------------------------------------------------------- |
| `source_table`| qname, NOT the user-facing pair name.                            |
| `column_name` | The column inside that table.                                    |
| `dt`          | **Vintage bucket label**, not the raw date. See `date_utils.bucket_date`. |
| `col_type`    | "numeric" / "string" / "date".                                   |
| `n_total` … `top_10` | Descriptive stats, **all stored as TEXT** — the canonical reason is cross-platform numeric typing. Read tutorial 06 §3 for the conversion rules. |
| `vintage_label`| Pretty label for the bucket (`2026Q1`, `2026-W12`).             |
| `length_avg`, `length_max`, `hash_sum` | "Coarse" stats added in the May 2026 lifeboat cleanup. Cheap to compute (no GROUP BY) and survive the *Quick* preset. `hash_sum` is the multiset checksum (tutorial 06 §5). |

Composite PK: `(source_table, column_name, dt)`.

### 1.3 `_column_meta` — discovered schema cache

`(source_table, column_name, data_type, source)`. Populated by
`discover_columns(conn, table_name)` (Oracle) and the platform-specific
`_discover_columns_*` helpers. Cleared and re-populated by
`/api/refresh-metadata`. Used by `compare.resolve_col_type` to figure out the
canonical type when left and right disagree.

### 1.4 `_table_pairs` — the pair definitions

Big table — the read-write target of every "edit pair" UI action. Holds:

- `pair_name` (PK), `table_left`, `table_right`, `source_left`, `source_right`
- `col_mappings` — JSON dict `{left_col: right_col}` mapping
- `col_include`, `col_exclude` — JSON arrays of glob patterns
- `col_rejected` — JSON `[[left_col, right_col], …]` of "no, never auto-match
  these two again"
- `col_type_overrides`, `col_type_overrides_right` — JSON dicts pinning a
  forced data-type (used by the comparison engine and the col-stats SQL builders)
- `col_rules` — legacy, unused. Don't write to it.

The pairs page (`web/static/pairs.js`) and the col-mapping page
(`web/static/col_mapping.js`) are the main mutators; `cli.py` mutates via
`cmd_match_columns`.

### 1.5 `_row_counts` — per-date row totals

`(source_table, dt, row_count)` with composite PK. `dt` here is the **raw**
date in YYYY-MM-DD canonical form (after `date_utils.parse_date` normalization),
*not* a vintage bucket. The bucket is applied at compare time.

### 1.6 `_row_comparison` — output of row reconciliation

`pair_name` (PK), `overlap_start`, `overlap_end`, JSON arrays
`matching_dates` / `excluded_dates` / `non_matching_dates`, plus
`where_left` / `where_right` so the col-stats SQL builders can reuse the same
filter. `query_time` records when it was last run.

### 1.7 `_col_comparison` — output of column reconciliation

Mirror of `_row_comparison` but for columns. `comparison_details` is JSON
holding per-column verdicts. The col-compare page reads this to render the
status badges.

### 1.8 `_sample_date` — vintage="sample" anchor

When a pair has `vintage: "sample-N"`, dtrack picks N representative dates per
side and stores them here so re-runs reuse the same set (deterministic
reconciliation across runs).

### 1.9 `_playground_history` — `/playground` audit log

One row per submitted query: engine, conn, sql, elapsed, n_rows, status,
note, ts_utc. The playground UI tails this table.

## 2. The JSON config (`dtrack.json`)

The user-facing config has one section per concern. The loader is
`config.load_unified_config(config_path)`; validators live in the same module.
A minimal config:

```json
{
  "pairs": {
    "trades_aws_vs_oracle": {
      "left":  {"name": "trades", "source": "oracle", "store": "ora_pb23"},
      "right": {"name": "trades", "source": "aws",    "store": "trade_db"},
      "vintage": "month",
      "fromDate": "2026-01-01",
      "toDate":   "2026-04-30",
      "col_map": {"trade_dt": "trade_date"}
    }
  },
  "date_types": {
    "ora_pb23.trades":   {"date_var": "trade_dt",   "date_type": "date"},
    "trade_db.trades":   {"date_var": "trade_date", "date_type": "yyyy-mm-dd"}
  }
}
```

### 2.1 The pair object

- `left` / `right`: `{name, source, store}`. `store` is the dataset/database/
  schema/catalog name relevant to the source (Oracle macro, Athena database,
  Databricks catalog.schema, CSV folder, …).
- `vintage`: controls how raw dates get bucketed (see `date_utils`). `"all"`
  produces one bucket per (table, column).
- `fromDate` / `toDate`: when present, generators inject `date_col BETWEEN`
  filters. The col-stats builder uses these to keep one date range across all
  buckets, so the comparison is apples-to-apples.
- `col_map`, `col_filter`, `col_type_overrides`, `excludeDates`: mirror of the
  `_table_pairs` columns; the UI writes both sides.

### 2.2 `date_types`

`{qname: {date_var, date_type, date_format?}}`. The qname is `store.name` for
sources that have a single namespace and `store.schema.name` for those that
don't (databricks). Authoritative resolution: `qualified_name(tbl_cfg)` in
`platforms/base.py`.

### 2.3 What the config does *not* hold

Computed results: row counts, column stats, comparison verdicts.
Those all live in `project.db`. Re-creating the project DB from the config is
expected — that is what `dtrack init` does.

## 3. Hydration rules (config ↔ db)

The web app uses the **DB as the source of truth** at request time. Specifically:

- When `/api/generate` is asked to build SQL for a pair, it loads the JSON
  config, then *hydrates* missing fields from `_table_pairs`. Look at
  `web/app.py:792–804`: if `col_map` is empty in JSON, it falls back to
  `get_pair_col_map_from_db`; same for `col_filter`.
- When the pairs UI saves a pair, it writes to **both** `_table_pairs` AND
  back into `dtrack.json` via `sync_db_to_config` so the file stays
  shareable.
- The CLI is the opposite: it loads the JSON, runs, and only writes back if
  the user explicitly asks (`save_and_pause` in `interact.py`).

## 4. `init_database` vs `refresh_database`

- `init_database(db_path)` creates an empty `project.db` with every table in
  `_SCHEMA`. Idempotent — uses `CREATE TABLE IF NOT EXISTS`. Called by
  `dtrack init` and on first `dtrack serve`.
- `refresh_database(db_path)` is **schema migration** for an existing db:
  reads the live SQLite, diffs against `_SCHEMA`, and runs `ALTER TABLE …
  ADD COLUMN …` for any column that is in `_SCHEMA` but not in the live db.
  It does **not** drop columns — that path requires manual SQL.

If you add a column to `_SCHEMA`, also bump `ensure_*` helpers below if your
column needs back-fill from existing rows (see `ensure_coarse_stat_columns`
for the May-2026 lifeboat columns).

## 5. Read patterns vs write patterns

Reads cluster into three shapes:

1. **Per-pair lookup**: `get_table_pair`, `get_pair_col_map_from_db`,
   `get_row_comparison`, `get_col_comparison`. These back every page render.
2. **Per-table aggregate**: `get_row_counts`, `get_col_stats`, `get_metadata`.
   The compare engine and the report renderer use these.
3. **List**: `list_table_pairs`, `list_playground_runs`, `list_tables`. UI
   index pages.

Writes cluster into two shapes:

1. **Upsert from CSV**: `upsert_row_counts`, `insert_col_stats` (which uses
   `INSERT OR REPLACE` via the composite PK). These are what the loader
   feeds into.
2. **Targeted patch**: `generic_upsert`, `generic_update`, `generic_delete`
   are tiny wrappers used by the web app for things like "edit one pair's
   col_include". They take a `where` dict and use `_get_table_schema` to
   validate column names, which keeps the user from poking arbitrary SQL.
