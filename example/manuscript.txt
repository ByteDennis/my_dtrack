================================================================================
  dtrack — Semi-Automated Data Validation Across Oracle, Athena, Databricks,
           Hive, and CSV
================================================================================


OVERVIEW
--------

dtrack is a config-driven CLI that compares row counts and column statistics
between database tables across different platforms. It extracts each side
directly (Python, no SAS), stores the results in a local SQLite database, and
produces HTML/Excel reports highlighting discrepancies. The workflow is
human-in-the-loop: the analyst reviews, corrects, and annotates results at key
checkpoints before proceeding.

Supported sources (the table "source" field):
    oracle      Oracle, via the oracledb driver
    aws         AWS Athena, via pyathena
    databricks  Databricks SQL warehouse, via databricks-sql-connector
    hadoop      Hadoop/Hive (HiveServer2), via impyla
    csv         A local CSV file, profiled in-process with DuckDB

A single pair can compare ANY two of these (Oracle vs Athena is the common
case, but Oracle vs Databricks, CSV vs CSV, etc. all work). The platform is
auto-detected from "source"; SQL is generated in the correct dialect.

Everything is driven by a single JSON config (pairs.json) that defines which
tables to compare, how columns map between sides, and accumulates decisions as
the workflow progresses.


THE WORKFLOW AT A GLANCE
------------------------

    pairs.json ──► extract ──► load ──► compare ──► HTML / Excel report
                      │           │         │
                      │           │         ▼
                      │           │     [ANALYST REVIEWS]
                      │           │     edits config, annotates
                      │           ▼         │
                      └──── project.db ◄────┘

The classic flow is the nine steps below, run in sequence. Steps 4 and 5 are
the manual checkpoints where the analyst intervenes. The row phase MUST finish
before column extraction — column SQL is filtered to the dates row-compare
matched (see Step 6).

Three ways to drive it:
    Web UI       dtrack serve project.db --config pairs.json   (browser; see end)
    just e2e     one command runs generate→run→load→compare per phase (justfile)
    Raw CLI      the steps below, run by hand

For day-by-day incremental column checks, see also compare-csv (a newer,
self-contained command that supersedes Steps 6-8 for many use cases).


================================================================================
STEP 0: Initialize the Database
================================================================================

    dtrack init project.db

Creates a fresh SQLite database with the system tables dtrack uses to store row
counts, column statistics, metadata, pair definitions, and comparison results.

    Options:
      --config PATH   Also write a starter config JSON (default: pairs.json next
                      to the db). Skipped if the file already exists.
      --force         Overwrite an existing database
      --refresh       Data-preserving schema upgrade (add new columns, rebuild
                      changed tables, keep existing data)
      --migrate       Alias of --refresh

    Output:
      project.db      SQLite database file
      pairs.json      Starter config (only with --config / default path)


================================================================================
STEP 1: Discover Columns
================================================================================

    dtrack load-columns project.db --config pairs.json

Loads column metadata (name + data type) for every table in the config. This
metadata drives platform-specific SQL later (e.g. knowing RPT_DT is a TIMESTAMP
triggers TRUNC() wrapping on Oracle).

    Options:
      --config        Unified config JSON (required)
      --csv FILE      Pre-collected metadata CSV (repeatable: --csv a.csv --csv b.csv)
      --columns-dir D Also dump per-table {qname}_columns.csv (COLUMN_NAME,DATA_TYPE)

    CSV format (for --csv):
      source,table,column_name,data_type
      oracle,CUST_DAILY,RPT_DT,TIMESTAMP
      oracle,CUST_DAILY,CUSTOMER_ID,NUMBER
      aws,cust_daily,amt,double

    Resolution order per table (first hit wins):
      1. a --csv metadata file
      2. inline "columns" / "columns_file" in the config
      3. an existing {qname}_columns.csv sidecar (from --columns-dir)
      4. live discovery from the platform's catalog:
           oracle      data dictionary (DESCRIBE / ALL_TAB_COLUMNS) via oracledb
           aws         information_schema.columns via pyathena
           databricks  DESCRIBE <catalog.schema.table>
           hadoop      DESCRIBE via HiveServer2
           csv         column names + inferred types from the file (DuckDB)
      ("processed"/CTE tables can't be auto-discovered — supply a sidecar.)

    Database effect:
      Populates _column_meta (qualified_name, column_name, data_type)

    Note: qualified_name = "<source>_<name>", e.g. oracle_cust_daily. Every CSV
    dtrack reads/writes is named {qualified_name}_{row|col|columns}.csv.


================================================================================
STEP 2: Extract Row Counts
================================================================================

Extraction is Python-direct — each command queries its backend and writes CSVs.
Use the per-platform command for each source in your config:

    dtrack gen-oracle     pairs.json --outdir ./csv/ --type row --db project.db
    dtrack gen-aws        pairs.json --outdir ./csv/ --type row --db project.db
    dtrack gen-databricks pairs.json --outdir ./csv/ --type row --db project.db

    Common options (all three):
      --type        row, col, or both (default: both)
      --db          project.db — REQUIRED for col extraction (reads where_map +
                    column metadata); harmless for row
      --vintage     Override bucketing (day/week/month/quarter/year/all/sample[@N])
      --workers     Parallel workers (default per platform: ORACLE_MAX_WORKERS=2,
                    ATHENA_MAX_WORKERS=8, DATABRICKS_MAX_WORKERS=4)
      --force       Skip confirmation prompts
      --from-date / --to-date   Incremental window (YYYY-MM-DD)
      --preset      quick | standard | detailed   (col stats depth; see "STATS")
      --stats-override KEY=on,KEY=off              (per-stat toggle)

    Alternatives:
      dtrack extract  project.db --config pairs.json --type row   # all platforms at once
      dtrack generate project.db --config pairs.json --type row   # write SQL, DON'T run
      dtrack run-sql  project.db --config pairs.json --type row   # run the generated SQL
    `generate` then `run-sql` is the review-the-SQL-before-it-hits-prod flow
    (mirrors the web UI). Hadoop uses generate+run-sql / extract; CSV is local.

    Output (./csv/):
      oracle_cust_daily_row.csv   Row counts per date for the Oracle table
      aws_cust_daily_row.csv      Row counts per date for the Athena table

    Row count CSV format (every platform produces the same schema):
      dt,row_count
      2023-01-02,1497
      2023-01-09,1523


================================================================================
STEP 3: Load Row Counts
================================================================================

    dtrack load-row project.db ./csv/ --config pairs.json --mode replace

Reads every {qname}_row.csv from the folder and loads it into the database.

    Options:
      --mode        upsert (default) — update existing dates, insert new ones
                    replace          — drop existing data, insert fresh
                    append           — insert all rows (may duplicate)
      --db          Database-name override
      --date-var    Date column name override

    Auto-detection:
      Date and count columns are matched by common aliases (dt, rpt_dt, date,
      snap_dt for dates; row_count, count, cnt for counts). Date format is
      detected from the first data row (YYYY-MM-DD, YYYYMMDD, DDMONYYYY, ...).

    Database effect:
      Populates _row_counts (qualified_name, dt, row_count)
      Updates _metadata with totals, source info, date format


================================================================================
STEP 4: Compare Row Counts                              [MANUAL CHECKPOINT]
================================================================================

    dtrack compare-row project.db --config pairs.json --html output/compare_row.html

The first human-in-the-loop step. For each pair, dtrack compares row counts by
date, then (without -y) pauses for analyst review.

    Options:
      --from-date / --to-date   Filter window (YYYY-MM-DD)
      -y, --yes                 Skip all prompts (use existing config state)
      --html                    Output HTML path (default: ./output/compare_row.html)
      --title / --subtitle      HTML report text

  What happens:

    1. Computes the overlap range and categorizes every date as matching,
       mismatched, left-only, or right-only.

    2. Prints a summary (overlap range, mismatched dates, misloads, match count).

    3. INTERACTIVE PROMPT (omit -y):
         cust_daily: 9 mismatched/missing dates
         Action? [s]kip pair / [i]gnore dates / [c]ontinue (default: c):
       - [s]kip     marks "skip": true — pair excluded from all later steps
       - [i]gnore   pick mismatched dates to add to the pair's ignore list
       - [c]ontinue proceed as-is

    4. Writes a per-pair row comparison to the DB (matching / mismatched /
       single-side dates). The set of count-MATCHING dates is what column
       extraction is later restricted to.

    5. Generates the HTML row-count report (per-pair banner, side-by-side
       range/total/runtime, expandable mismatch detail).

  Config fields this step may write:
      skip, ignore_rows, plus the report annotations time_map / comment_map you
      can fill in by hand (shown as tooltips in the HTML).


================================================================================
STEP 5: Match Columns                                   [MANUAL CHECKPOINT]
================================================================================

    dtrack match-columns project.db --config pairs.json

Maps column names between left and right (e.g. AMT vs amount). Auto-matches what
it can by case-insensitive name, then (without --yes) asks the analyst to
resolve the rest.

    Options:
      --mode merge    keep existing col_map, add new matches (default)
      --mode replace  discard existing col_map, start fresh
      --map-csv CSV   explicit mappings (pair,left,right); overrides auto + rules
      --yes           non-interactive: keep auto-matches, skip the manual prompt

  Interactive mapping accepts type lines with wildcards:
      > AMT          amount
      > RPT_*        rpt_*          (expands against the real column lists)

  Config field written:
      col_map   { "<left col>": "<right col>", ... }   e.g. {"AMT": "amount"}


================================================================================
STEP 6: Extract Column Statistics
================================================================================

    dtrack gen-oracle pairs.json --outdir ./csv/ --type col --db project.db
    dtrack gen-aws    pairs.json --outdir ./csv/ --type col --db project.db

Same commands as Step 2, now with --type col and --db pointing at the database.
--db is critical here: it lets dtrack read the row comparison (Step 4) and
column metadata (Step 1) to generate FILTERED queries.

  Key behaviors:
    - Only extracts columns present in col_map (Step 5).
    - Restricts to the count-matching dates row-compare wrote (so STEP 4 MUST
      run first). The `just e2e` pipeline enforces this ordering.
    - Buckets by vintage:
        day | week | month | quarter | year   one row per bucket
        all                                    one row aggregating all dates
        sample                                 random sample of dates (n=100
                                               default; reproducible via SEED)
        sample@50                              random sample of exactly 50 dates
    - Computes the stats selected by --preset / --stats-override (see STATS).

  Review-then-run variant (recommended for prod): split generation and execution
      dtrack generate project.db --config pairs.json --type col --outdir ./
      # inspect ./csv/extract_col.<platform>.sql, then:
      dtrack run-sql  project.db --config pairs.json --type col --outdir ./

  Column stats CSV (every platform produces the same schema):
      dt,column_name,col_type,n_total,n_missing,n_unique,mean,std,min_val,max_val,top_10,length_avg,length_max,hash_sum


================================================================================
STEP 7: Load Column Statistics
================================================================================

    dtrack load-col project.db ./csv/ --config pairs.json --mode replace

Reads {qname}_col.csv files into the database.

    Options:
      --mode   upsert (default) | replace

    Database effect:
      Populates _col_stats; updates _metadata with vintage and source info.


================================================================================
STEP 8: Compare Column Statistics
================================================================================

    dtrack compare-col project.db --config pairs.json --html output/compare_col.html

Compares column-level statistics between paired tables and writes an HTML (and
optional Excel) report.

    Options:
      --from-date / --to-date   Filter window
      --no-date-filter          Compare all vintages (skip the date-match filter)
      --vintage month|quarter|year   Vintage grouping in the HTML
      -y, --yes                 Skip prompts
      --html                    Output path (default: ./output/compare_col.html)
      --excel PATH              Also write an Excel report (default: HTML path + .xlsx)
      --title / --subtitle      HTML report text

  What happens:
    1. Restricts to the matching dates from row comparison (unless --no-date-filter).
    2. For each column in col_map, compares left vs right stats.
    3. Resolves type disagreement: numeric+numeric → numeric, else categorical.
       Override with "col_type_overrides": {"ACCOUNT_ID": "categorical"}.
    4. Flags differences (count diffs non-zero; mean/std beyond tolerance).
    5. Generates the HTML/Excel report (per-column, per-vintage breakdown).


================================================================================
COMPARE-CSV: incremental, self-contained column comparison
================================================================================

    dtrack compare-csv project.db --config pairs.json --vintage month

A newer command that replaces Steps 6-8 for incremental checks. Per vintage
window it pulls each side to a temporary CSV, computes the stats LOCALLY in
DuckDB, upserts into _col_stats, and compares — bounded memory, no single huge
backend col scan. It is self-contained: it discovers count-matching dates itself
(reusing _row_counts if already loaded), so NO prior compare-row is required.

    Options:
      --pair NAME            Restrict to one pair (default: all non-skipped)
      --vintage day..year    One pull window per bucket (default: pair's vintage, else day)
      --from-date / --to-date
      --preset / --stats-override            (see STATS)
      --sample N|FRAC        Cut the download (REQUIRES --key):
                               integer  = N fixed keys/window (raw-key IN-list)
                               0<FRAC<=1 = fraction via a hash-bucket pushdown
                                           (no key list; scales to billions —
                                           same rows land on BOTH sides)
      --key COLS             Composite row key (comma-separated left columns;
                             right resolved via col_map). Required for --sample.
      --data-dir DIR         Folder for the per-window CSVs (must exist) — keep
                             big pulls off a small disk. Default: system temp.
      --workers N            Parallelism for the LOCAL per-column stat compute
                             (windows always run sequentially; columns parallel)
      --keep-csv             Keep the per-window tmp CSV/config dirs
      --force                Re-pull every window (ignore skip-cache)
      --verbose              Print full backend SQL (default: one concise line/step)
      --clean marks|cache|all   Reset before running (signature / +stats+caches /
                                +delete project.db & wipe --data-dir)

    Skip-cache is the DEFAULT: already-loaded windows are skipped, and a changed
    --sample/--key/col_filter/--preset/--vintage auto-triggers a re-pull.
    Persists project.db + {pair}_compare_col.csv; the per-window pulls are scratch.


================================================================================
SAMPLING & DEBUG HELPERS
================================================================================

  sample-key — unified composite-key sampler (supersedes sample-hash + col-sample)
      dtrack sample-key project.db --config pairs.json --key acct,sub
        default     dump sampled key values + backend hash16 to Excel (debug hash_sum)
        -n -1       report KEY combinations unmatched across sides (anti-join)
        --gen-col   persist the sampled key IN (...) into where_map + generate col SQL
                    (then run with `run-sql --type col`); add --cols / --sample-cols
                    to limit columns, --keys / --keys-file to supply keys explicitly
      Use this to spot-check WHY a column's hash_sum differs: pull the same keys
      from both sides and diff the raw values.

  sample-hash / col-sample — the older single-purpose forms (value+hash dump /
  key-sample → col SQL). sample-key does both; prefer it for new work.


================================================================================
THE CONFIG FILE: pairs.json
================================================================================

The config is the single source of truth — input AND accumulated output. It
starts minimal (pair definitions) and grows as the workflow writes decisions
back to it.

  {
    "metadata": {
      "title": "Row Count Comparison",
      "subtitle": "updates every Thursday",
      "col_title": "Column Statistics Comparison",
      "col_subtitle": "updates first Thursday of every month"
    },
    "pairs": {
      "cust_daily": {
        "left": {                            // Oracle side
          "name": "cust_daily",              //   dtrack name (qname = source_name)
          "table": "CUST_DAILY",             //   raw table in the source DB
          "source": "oracle",                //   oracle|aws|databricks|hadoop|csv
          "date_col": "RPT_DT",              //   date column in source table
          "date_transform": "TRUNC({col})",  //   optional SQL wrapper for the date col
          "conn_macro": "pb23",              //   connection: Oracle DSN macro
          "where": "STATUS = 'A'",           //   base filter (always applied)
          "vintage": "week"                  //   date bucketing granularity
        },
        "right": {                           // Athena side
          "name": "cust_daily",
          "table": "cust_daily",
          "source": "aws",
          "conn_macro": "analytics_db",      //   connection: Athena database
          "date_col": "rpt_dt",
          "where": "",
          "vintage": "week"
        },

        // --- populated by the workflow ---
        "col_map":   { "AMT": "amount", "REGION": "region" },   // Step 5
        "time_map":  { "row": {"left": "42 sec", "right": "112 sec"} },  // analyst
        "comment_map": { "row": {"left": "filtered STATUS='A'", "right": ""} },

        // --- per-pair tuning (all optional) ---
        "skip": false,                       // true = excluded from the workflow
        "ignore_rows":    ["2023-03-06"],    // dates shown but not flagged
        "ignore_columns": ["LOAD_DT"],       // columns shown but not flagged
        "col_type_overrides": { "ACCOUNT_ID": "categorical" },
        "key": "acct,sub",                   // composite key for --sample / sample-key
        "sample": 500,                       // int = N keys, float = fraction
        "strict": true                       // normalize values before comparing
      }
    }
  }

  conn_macro by platform:
      oracle      DSN macro name (resolved via DTRACK_ORACLE_MACROS / LDAP_DSN)
      aws         Athena database name
      databricks  catalog.schema  (or just schema, with DB_DEFAULT_CATALOG)
      hadoop      Hive DSN
      csv         path to the CSV file   (there is NO separate csv_path field)

  vintage:  day | week | month | quarter | year | all | sample | sample@N
            (compare-csv accepts day..year only).


================================================================================
STATS PRESETS
================================================================================

Column extraction computes a configurable set of statistics. Pick depth with
--preset, or toggle individual stats with --stats-override:

    quick     n_total, n_missing, min/max, length          (cheap)
    standard  + n_unique, hash_sum
    detailed  + top_10 (most-frequent values)              (default-ish, fullest)

    --stats-override n_unique=on,hash_sum=off
        keys: n_total, n_missing, n_unique, min_max, length, hash_sum, top_10

    n_unique is an EXACT COUNT(DISTINCT) (never an approximate). hash_sum is an
    order-independent checksum of the column — when only hash_sum differs on
    otherwise-equal stats, you have a real value difference (use sample-key to
    inspect). "strict" (per-pair or DTRACK_STRICT=1) normalizes values
    (trim/case/numeric/date canonicalization) so presentation drift doesn't
    register as a difference.


================================================================================
ENVIRONMENT VARIABLES
================================================================================

Set in an env file (.env / dtrack.conf / dtrack.env, auto-discovered) or pass
--env PATH. Verify resolution with `dtrack doctor` (env only, no DB connect).

  Oracle:
    <MACRO>_USR / <MACRO>_PWD     per-DSN credentials (e.g. PB23_PWD), tried first
    PCDS_USR / PCDS_PWD           credential fallback
    LDAP_DSN                      resolve an Oracle DSN via LDAP
    DTRACK_ORACLE_MACROS          inline macro→DSN map (pb40:svc_x,pb50:svc_y)
    DTRACK_ORACLE_MACROS_FILE     same, from a file

  AWS / Athena:
    AWS_DEFAULT_REGION            region (e.g. us-east-1)
    AWS_S3_WORK_GROUP             Athena workgroup
    AWS_S3_STAGING_DIR            S3 staging dir for Athena results
    AWS_USR / AWS_PWD / AWS_HOST  proxy auth (builds HTTPS_PROXY)
    AWS_ACCESS_KEY_ID / AWS_TOKEN_URL / AWS_ARN_URL   STS creds flow

  Databricks:
    DB_PROFILE / DB_HTTPS         OAuth profile + warehouse http_path (BOTH required)
    DB_DEFAULT_CATALOG            catalog when conn_macro is schema-only

  Hadoop / Hive:
    HADOOP_DSN                    Hive DSN
    KRB5_KTNAME / KRB5_CONFIG / KRB5CCNAME   Kerberos
    ODBCSYSINI / ODBCINI          ODBC config dirs

  Concurrency (per-platform col workers; or use --workers):
    ORACLE_MAX_WORKERS (2)  HADOOP_MAX_WORKERS (1)  ATHENA_MAX_WORKERS (8)
    DATABRICKS_MAX_WORKERS (4)  CSV_MAX_WORKERS (4)

  Toggles / tuning (defaults in parens):
    DTRACK_STRICT                 1 = global STRICT value normalization
    DTRACK_QUERY_CACHE            0 = disable the query cache
    DTRACK_ID_DETECTION (1)       0 = skip ID-column detection
    DTRACK_DATABRICKS_REST (1)    0 = Thrift connector instead of REST
    DTRACK_DATABRICKS_DISPOSITION (EXTERNAL_LINKS)   INLINE = 25 MiB-capped pulls
    DTRACK_DATABRICKS_TIMEOUT (1800) / _SOCKET_TIMEOUT (600) / _RETRIES (2)
    SEED (2025)                   reproducible vintage=sample date pick
    DTRACK_LOG / DTRACK_LOG_LEVEL (DEBUG)   log file / level

================================================================================
INCREMENTAL UPDATES
================================================================================

dtrack tracks the loaded date range in _metadata, so you only pull new dates:

    dtrack query project.db \
        "SELECT table_name, min_date_loaded, max_date_loaded FROM _metadata"

    dtrack gen-aws    pairs.json --type row --from-date 2025-03-14 --db project.db
    dtrack gen-oracle pairs.json --type row --from-date 2025-03-14 --db project.db

--from-date / --to-date inject WHERE bounds on each table's date column before
extraction; min/max_date_loaded expand automatically after loading. (compare-csv
takes the same flags and is the simplest incremental path.)

The query command gives direct SQL access to the database:
    dtrack query project.db "SELECT * FROM _metadata"
    dtrack query project.db "DELETE FROM _col_stats WHERE qualified_name='...'" --write


================================================================================
SEMI-AUTOMATED DESIGN
================================================================================

The workflow alternates automated steps with manual checkpoints:

  AUTOMATED                                MANUAL
  ─────────                                ──────
  init, load-columns                       (none)
  gen-oracle/aws/databricks (extract)      (none)
  load-row, load-col                       (none)
  compare-row                              Skip pair? Ignore dates? Annotate?
  match-columns                            Map unmatched columns? Use wildcards?
  compare-col                              (review the report)

Automated row comparison often produces imperfect results — some dates mismatch
because of known loads, holidays, or timing. The analyst decides which
discrepancies matter; those decisions persist in the config and carry forward to
column extraction, so only truly comparable date ranges are profiled. Pass -y /
--yes to skip the prompts and reuse existing config state (scheduled re-runs).


================================================================================
WEB UI
================================================================================

dtrack includes a web UI for running the workflow from a browser.

    dtrack serve project.db --config pairs.json --port 8080
    # open http://localhost:8080

It shows per-pair loaded date ranges, step buttons (extract / load / compare),
a scrolling command log, a SQL query box, and links to the generated reports.
The from-date field auto-fills with max_date_loaded + 1 day, making incremental
runs a single click. Stack: FastAPI + uvicorn + vanilla JS, no build step.
Install with: pip install 'dtrack[web]'.
